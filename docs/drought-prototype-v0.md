# 가뭄 프로토타입 설계 v0

## 문서 상태

```text

IMPLEMENTATION AUTHORIZATION = M0 + M1 + M2 + M3
M1 IMPLEMENTATION AUTHORIZATION = GRANTED / 2026-09-01
M2 IMPLEMENTATION AUTHORIZATION = GRANTED / 2026-09-01
M3 IMPLEMENTATION AUTHORIZATION = GRANTED / 2026-09-01
M4 DETAILED DESIGN AUTHORIZATION = GRANTED / 2026-09-04
IMPLEMENTATION STATUS = M0 COMPLETE / PASS / M1 COMPLETE / PASS / M2 COMPLETE / PASS / M3 COMPLETE / MECHANICS PASS
AUTOMATED VERIFICATION = M0 + M1 + M2 + M3 LOCAL / LINUX / WINDOWS PASS
GUI VERIFICATION = WINDOWS EDITOR F5 PASS / 2026-09-01
FULL ACCEPTANCE = M0 + M1 + M2 + M3 MECHANICS PASS / M3 BEHAVIOR OBSERVED

NEXT GATE = DOCUMENT MERGE VERIFICATION / SEPARATE M4 IMPLEMENTATION AUTHORIZATION
```

이 문서는 첫 프로토타입의 잠정 검증 범위를 기록한다. 게임 엔진과 프로그래밍 언어는 가뭄 프로토타입에 한해 잠정 결정했다. 수치와 UI 상세는 아직 잠정안이며, 구현된 M1~M3 경계는 결정 18~22의 해당 계약과 동결 artifact로 고정했다.

## 1. 검증 목적

첫 프로토타입은 그래픽, 전투, 대사 생성 또는 콘텐츠 양을 검증하지 않는다. 다음 질문에 답하는 것이 목적이다.

> 평소 규칙을 잘 지키던 주민이 가뭄으로 가족이 굶고, 촌장에게 도움을 거절당한 뒤 곡식을 훔치는 선택에 인과적으로 도달할 수 있는가? 그리고 그 경험이 이후 판단을 바꾸는가?

성공의 핵심은 특정한 결말이 나오는 것이 아니다. 서로 다른 결과가 발생하더라도 그 판단과 변화의 원인을 역추적할 수 있어야 한다.

## 2. 잠정 세계 범위

- 장소: 외부 세계와 연결된 마을 1개
- 인구 상한: 인간 NPC 60명
- 권력 구조: 촌장과 소수의 비공식 영향력자
- 외부 세계: 직접 시뮬레이션하지 않고 날씨, 세금, 행상인, 유민, 소문 등의 입력으로만 존재
- 최초 위기: 가뭄과 그에 따른 수확 감소·식량 부족
- 플레이어: 공동창고의 하급 관리 보조 1명. NPC와 동일한 인과 규칙에 묶이며 배우자 1명과 어린 자녀 1명이 있음

60명 전원을 매 순간 같은 밀도로 계산하는 것은 목표가 아니다. 다만 이 단계에서는 모든 주민에게 최소한의 신원, 가구, 생업, 관계 및 판단 상태가 존재해야 한다.

## 3. 가뭄의 인과 순서

가뭄은 즉시 `식량 감소`를 적용하는 단일 팝업이 아니다. 잠정적인 인과 순서는 다음과 같다.

1. 강수 부족이 발생한다.
2. 예상 수확량이 감소한다.
3. 식량 가격과 불안이 상승한다.
4. 가구별 비축량이 서로 다른 속도로 감소한다.
5. 촌장과 영향력자들이 배급·비축·통제 방식을 판단한다.
6. 주민들이 자신의 상태, 관계, 인식에 따라 행동을 선택한다.
7. 선택의 결과가 자원, 관계, 기억, 평판 및 이후 판단에 영향을 준다.

## 4. 최초 행동 후보

주민이 모든 행동을 항상 선택할 수 있는 것은 아니다. 정보, 자원, 관계 및 기회가 행동 가능 여부를 제한한다.

- 현재 배급을 따른다.
- 촌장에게 추가 식량을 요청한다.
- 이웃과 남은 식량을 나눈다.
- 배급 방식에 공개적으로 항의한다.
- 공동창고의 곡식을 훔친다.
- 가족과 마을을 떠난다.

행동에는 사건 전용 결과를 직접 나열하기보다 공통 의미를 부여한다. 예를 들어 `공동창고의 곡식을 훔친다`에는 가족 보호, 규칙 위반, 처벌 위험, 즉각적 생존 이익, 공동체 피해, 비밀 유지 필요 등의 의미가 포함될 수 있다.

## 5. 최초 내부 요소

아래 목록은 확정된 전체 트레잇 체계가 아니다. 가뭄 실험에 필요한 최소 후보만 기록한다.

### 5.1 일반 성향 후보

| 성향 | 잠정 작동 정의 |
|---|---|
| 위험 감수 | 처벌·부상·불확실성이 있는 행동에서 느끼는 심리적 비용에 영향 |
| 공감성 | 타인의 손익을 자신의 판단에 반영하는 정도에 영향 |
| 자기통제 | 즉각적 욕구와 장기적 결과 사이의 선택에 영향 |
| 규범 중시 | 절도·기만·명령 위반에서 느끼는 내적 저항에 영향 |

### 5.2 성향과 분리할 요소

| 종류 | 예시 |
|---|---|
| 가치관 | 가족 우선, 공동체 애착 |
| 현재 상태 | 굶주림, 공포, 분노 |
| 관계 | 촌장에 대한 신뢰, 특정 인물에 대한 애정·원한 |
| 자원 | 개인·가구 식량, 재산 |
| 인식 | 공동창고 비축량과 배급 공정성에 대한 믿음 |
| 중요 기억 | 도움을 요청했지만 거절당함, 절도를 목격함 |
| 사회적 평가 | 도둑, 충신, 겁쟁이 등 타인이 부여한 평판 |

`충성`처럼 상대에 따라 달라지는 요소는 단일한 일반 성향으로 환원하지 않는다. 약속과 의무를 중시하는 가치관과 특정 인물·조직에 대한 신뢰 및 헌신을 구분한다.

## 6. 예시 인과 경로

1. 규범을 중시하고 촌장을 신뢰하는 주민은 초기 배급을 따른다.
2. 가뭄이 지속되고 부양가족의 굶주림이 심해진다.
3. 주민이 촌장에게 도움을 요청하지만 거절당한다.
4. 촌장에 대한 신뢰와 정당성 인식이 하락하고 분노와 절박함이 증가한다.
5. 가족 보호의 기대효용이 규범 위반과 처벌 위험의 비용을 넘으면 절도를 선택할 수 있다.
6. 절도 결과는 죄책감, 안도감, 자기합리화, 발각 여부 및 타인의 평가를 서로 다르게 변화시킨다.
7. 변화한 주민은 이후의 배급, 도적 침입 또는 촌장의 명령에서 이전과 다른 판단을 내릴 수 있다.

이 경로는 작성된 줄거리가 아니라 가능한 결과 중 하나다. 같은 시작에서도 촌장의 배급, 주민의 관계, 정보, 선택 및 통제된 불확실성에 따라 다른 결과가 나올 수 있어야 한다.

## 7. 검증 및 반증 기준

### 7.1 필수 검증

- 같은 초기 상태와 같은 난수 시드에서 결과를 재현할 수 있다.
- 특정 판단이 어떤 성향·상태·관계·인식·기억의 영향을 받았는지 추적할 수 있다.
- 의미 있는 경험이 관련된 내부 요소만 변화시킨다.
- 변화한 내부 요소가 이후 행동 선택에 실제로 영향을 준다.
- 사건을 알지 못하는 NPC가 그 사건에 직접 반응하지 않는다.
- 플레이어에게 상세 수치를 공개하지 않더라도 개발자는 내부 인과를 확인할 수 있다.

### 7.2 반증 질문

- 가뭄이 없다면 같은 주민이 절도를 선택하는가?
- 촌장이 충분한 식량을 제공하면 절도를 선택하는가?
- 부양가족이 없다면 같은 위험을 감수하는가?
- 경비와 처벌 위험이 커지면 다른 행동을 선택하는가?
- 촌장의 공동창고와 무고한 이웃의 식량을 동일하게 취급하는가?
- 절도 사실을 모르는 주민도 해당 인물을 도둑으로 평가하는가?

시스템이 이 차이를 설명하지 못하면 인과 모델은 검증되지 않은 것으로 본다.

## 9. 승인된 잠정 설계 1~6

아래 여섯 항목은 가뭄 프로토타입에 한정해 승인된 잠정 설계다. 전체 게임의 영구 규칙으로 확정하지 않으며, 실제 검증 결과에 따라 수정하거나 폐기할 수 있다.

### 결정 1. 첫 플레이어 캐릭터

첫 플레이어 캐릭터는 마을 공동창고의 하급 관리 보조로 고정한다.

- 공식 권력은 없음
- 공동창고의 대략적인 비축량을 알 수 있음
- 촌장과 창고 책임자에게 접근할 수 있음
- 주민들의 식량 사정을 접할 수 있음
- 배우자 1명과 어린 자녀 1명이 있음
- 처음에는 촌장의 권위를 대체로 인정함
- 규범 중시와 자기통제가 비교적 높음
- 플레이어가 조작하지 않을 때는 다른 NPC와 같은 판단 규칙을 적용함

배우자와 자녀는 배경 설정이 아니라 독립된 NPC다. 가족의 굶주림과 배우자의 판단은 플레이어의 선택 조건과 결과에 실제로 영향을 준다.

### 결정 2. 게임 시간의 최소 단위

기본 시간 단위는 `1일`이다. 실시간이나 시간 단위 계산은 사용하지 않는다.

- 매일: 식량 소비, 굶주림, 건강 및 자원 상태 갱신
- 사건 발생 시: 관련 인물만 즉시 판단
- 매주: 장기 목표와 성향 변화 압력 정리
- 계절 단위: 강수량, 수확량 및 가뭄 진행 갱신
- 특별한 사건이 없을 때: 1일 또는 7일 건너뛰기 허용

절도처럼 밤에 일어나는 사건은 별도의 시간제 시뮬레이션을 만들지 않고 `야간 행동`이라는 상황으로 표현한다.

### 결정 3. 행동 생성과 판단 방식

설명 가능한 효용 기반 판단 방식을 사용한다.

#### 행동 후보 생성

모든 NPC가 모든 행동을 검토하지 않는다. 현재 인식, 자원, 관계, 위치 및 기회상 실행 가능한 행동만 후보가 된다. 공동창고의 존재나 위치를 모르는 주민에게는 `공동창고에서 훔친다`가 후보로 생성되지 않는다.

#### 행동 평가

각 행동은 다음 요소로 평가한다.

```text
생존 필요
+ 현재 목표와의 부합
+ 가치관·성향과의 부합
+ 관계에 미칠 것으로 믿는 영향
+ 예상되는 이익
- 인식하고 있는 위험
- 성향과의 내적 충돌
- 기존 행동을 바꾸는 비용
+ 제한된 난수
```

NPC는 실제 세계가 아니라 자신이 알고 있다고 믿는 정보를 기준으로 판단한다. 점수가 명확하게 높은 행동은 그대로 선택하고, 여러 행동의 점수가 비슷할 때만 고정된 난수 시드를 이용한다. 같은 상태와 같은 시드에서는 같은 결과가 재현되어야 한다.

#### 의도 기록

같은 행동이라도 선택 당시 가장 강했던 목표를 의도로 기록한다. 가족을 살리기 위한 절도, 자기 생존을 위한 절도, 이익을 위한 절도, 촌장에게 복수하기 위한 절도는 서로 다른 인과로 취급한다.

#### 플레이어와 NPC

- NPC는 평가 결과에 따라 행동을 선택함
- 플레이어는 실행 가능한 행동 중 직접 선택함
- 성향에 어긋나는 선택도 금지하지 않음
- 성향 충돌에 따라 스트레스, 죄책감, 수행 불이익 및 관계 변화가 발생할 수 있음
- 개발 기록에는 상위 행동 후보와 선택 이유를 보존함
- 플레이어에게는 정확한 내부 점수를 공개하지 않음

### 결정 4. 성향 변화의 임계값과 속도

성향은 내부적으로 `0~100` 범위를 사용하되 플레이어에게 정확한 수치를 공개하지 않는다.

| 요소 | 변화 속도 |
|---|---|
| 굶주림·공포·분노 | 즉시 크게 변할 수 있음 |
| 신뢰·애정·원한 | 사건에 따라 즉시 변하지만 중간 속도 |
| 일반 성향·가치관 | 의미 있는 경험이 누적될 때 천천히 변화 |
| 평판 | 사건을 알게 되고 믿은 NPC별로 별도 변화 |

성향은 행동 직후 직접 크게 변경하지 않고 `변화 압력`을 누적한다.

- 사소한 행동: 성향 변화 없음
- 의미 있는 선택: 변화 압력 `±1~3`
- 큰 비용을 감수한 결정적 선택: 변화 압력 `±4~8`
- 극단적인 트라우마: 예외적으로 즉시 소폭 변화하고 중요 기억 생성
- 주간 정리: 누적 압력에 따라 성향별 최대 `±2` 변화, 잔여 압력은 이월

자발적 선택, 사전에 인식한 위험, 기존 성향과의 실제 충돌, 직접 경험한 결과 및 책임 인식이 강할수록 변화 압력이 커진다. 동일한 저위험 행동의 반복 효과는 감소시켜 성향 수치 노가다를 막는다.

### 결정 5. 기억의 유지·망각·압축

객관적인 사건 기록과 NPC가 주관적으로 보유한 기억을 분리한다.

#### 객관적 사건 기록

개발 검증과 연대기 생성을 위해 실제 발생한 사건, 행위자, 결과, 목격자 및 정보 전달 경로를 기록한다.

#### NPC 기억

NPC는 사건 전체가 아니라 자신이 보거나 들은 내용만 기억한다. 기억에는 다음을 포함한다.

- 사건 또는 소문의 식별자
- 관련 인물
- 자신이 인식한 행동과 결과
- 직접 목격 또는 전언 여부
- 정보 제공자와 신뢰도
- 감정적 강도
- 발생 시점
- 비밀 여부

#### 기억 단계

- 최근 기억: 최근 14일의 관련 경험
- 중요 기억: 판단과 관계에 계속 영향을 주는 사건, 최대 24개
- 핵심 기억: 배신, 가족 사망, 생명 구조 등 정체성을 형성한 사건, 최대 8개

중요도가 낮아진 기억은 단순 삭제하지 않고 관계와 인상으로 압축할 수 있다. 세부 기억이 희미해져도 이미 발생한 관계·성향 변화는 원래대로 돌아가지 않는다.

### 결정 6. 정보와 소문의 전달

정보는 모든 주민에게 즉시 공개되지 않는다. 다음 정보를 가진 구조화된 정보 묶음이 인물 사이를 이동한다.

```text
무슨 일이 있었다고 주장하는가
누가 말했는가
원래 정보원은 누구인가
직접 목격인지 전언인지
현재 신뢰도
비밀 여부
```

정보는 직접 목격, 가족 간 대화, 친구·이웃과의 대화, 촌장의 공개 발표, 공공장소의 소문, 의도적인 고발이나 비밀 누설을 통해 전달된다.

하루의 사회적 접촉에서 중요한 정보만 제한적으로 전달한다. 전달 가능성은 친밀도, 중요도, 말하기 성향, 비밀 유지 의무 및 위험에 영향을 받는다.

- 정보 제공자를 신뢰하면 수용 가능성이 높아짐
- 기존 믿음과 충돌하면 의심할 수 있음
- 확신이 낮으면 확인 행동을 선택할 수 있음
- 정보를 들었더라도 믿은 NPC만 판단과 평판을 변경함

첫 프로토타입에서는 전달 과정에서 사건 내용을 무작위로 왜곡하지 않는다. 전달 단계가 늘어날수록 신뢰도만 낮아진다. 의도적인 거짓말은 추후 별도 행동으로 다룬다.

## 10. 승인된 잠정 설계 7

### 결정 7. 제한된 정성적 판단 단서

정확한 수치와 확정 결과는 감추되, 플레이어 캐릭터가 합리적으로 알 수 있는 위험, 내적 충돌 및 정보의 신뢰성은 제공한다.

선택지마다 다음 중 가장 중요한 단서를 최대 3개까지 보여준다.

1. 성향·가치관과의 부합 또는 충돌
2. 캐릭터가 알고 있는 직접적인 위험과 이익
3. 판단에 사용된 정보의 출처와 신뢰 성격

예시는 다음과 같다.

```text
[내면] 가족을 보호하려는 마음과 강하게 부합한다.
[내면] 당신의 규범 의식과 심하게 충돌한다.
[확인] 오늘 밤 경비가 평소보다 적다는 것을 알고 있다.
```

정보 출처는 숫자 대신 다음과 같이 표현한다.

| 표시 | 의미 |
|---|---|
| `[확인]` | 직접 보거나 자신의 업무로 알고 있음 |
| `[전언]` | 신원이 분명한 사람에게 들음 |
| `[소문]` | 출처가 불확실하거나 여러 전달 단계를 거침 |
| `[추정]` | 현재 지식과 경험으로 예상함 |
| `[내면]` | 자신의 성향·욕구·감정에서 발생한 반응 |

단서는 무작위로 숨기지 않는다. 직접 목격한 사실, 직업상 아는 정보, 기억한 사건, 전달받은 정보, 자기 성향과 감정 및 현재 지식으로 합리적으로 추론할 수 있는 위험은 항상 표시할 수 있다.

다음 정보는 제공하지 않는다.

- NPC의 숨겨진 속마음
- 목격하거나 전해 듣지 않은 비밀
- 행동의 확정 성공 여부
- 미래에 발생할 연쇄 결과
- 실제 확률과 내부 점수
- 소문의 진위를 판정한 시스템 정답

첫 프로토타입에는 별도의 `관찰력` 능력치를 추가하지 않는다. 직업, 직접 관찰, 관계, 기억 및 전달받은 정보로 단서의 범위를 결정한다.

선택 이후에도 내부 수치 대신 플레이어가 느끼거나 관찰할 수 있는 결과만 전달한다. 성향의 작은 수치 변동은 알리지 않고, 변화가 충분히 누적되어 표현 단계가 달라지거나 중요한 자기 인식이 생겼을 때만 정성적으로 알린다.

```text
정확한 수치 공개 = 금지
확정 결과 예고 = 금지
전지적 정보 제공 = 금지
성향 부합·충돌 표시 = 허용
인지 가능한 위험 표시 = 허용
정보 출처·신뢰 성격 표시 = 필수
선택당 핵심 단서 = 최대 3개
단서 제공 기준 = 플레이어 캐릭터의 지식·기억·관계·직업
```

## 11. 승인된 잠정 설계 8

### 결정 8. 게임 엔진과 프로그래밍 언어

가뭄 프로토타입은 다음 조합을 사용한다.

```text
ENGINE = Godot 4.7.2 stable
EDITION = Standard
LANGUAGE = GDScript
TYPING = STATIC TYPING REQUIRED
FIRST TARGET = Windows Desktop
PROJECT MODE = 2D / UI 중심
```

이 결정은 완성형 게임의 영구 기술 선택이 아니라 가뭄 프로토타입을 낮은 진입 비용으로 검증하기 위한 잠정안이다.

#### 버전 정책

- 개발판인 Godot 4.8 계열은 사용하지 않음
- 가뭄 프로토타입이 종료될 때까지 Godot 4.7.2에서 업그레이드하지 않음
- 버전 변경이 필요하면 별도 설계 변경과 회귀 검증을 거침

#### 언어 정책

- GDScript의 정적 타입 표기를 기본이 아니라 필수로 사용함
- 주요 변수, 함수 매개변수 및 반환값에 타입을 명시함
- 빠른 작성 편의를 이유로 무제한 Dictionary와 Variant 의존을 허용하지 않음
- 성능 문제가 실제 측정으로 확인되기 전에는 C#이나 네이티브 확장을 추가하지 않음

#### 구조적 제한

시뮬레이션과 화면 표현을 분리한다.

```text
시뮬레이션 계층
- NPC 데이터
- 가구와 자원
- 관계와 기억
- 사건과 정보
- 행동 후보와 판단
- 시간 진행

표현 계층
- 선택지 화면
- 인물 정보
- 마을 상태
- 사건 기록
```

- NPC 60명을 각각 독립적인 화면 Node로 구현하지 않음
- NPC는 기본적으로 데이터 객체로 존재함
- UI는 시뮬레이션 상태를 읽어 표시하고 플레이어의 행동 요청을 전달함
- 버튼 코드가 성향·관계·자원을 직접 변경하지 않음
- 플레이어와 NPC가 같은 행동 처리 경로를 사용함
- 화면을 표시하지 않는 상태에서도 같은 입력과 난수 시드로 같은 결과가 나와야 함

행동 처리 흐름은 다음 경계를 따른다.

```text
UI 입력
→ 행동 요청
→ 실행 가능성 확인
→ 결과 계산
→ 세계 상태 변경
→ UI 갱신
```

#### 데이터와 저장의 초기 방향

- 성향과 행동 정의: Git에서 비교 가능한 텍스트 기반 데이터
- 실행 중 세계 상태: 정적 타입 GDScript 객체
- 저장파일: 개발자가 검사할 수 있는 명시적 구조
- 난수 시드: 저장 상태에 반드시 포함
- 개발 로그: 행동 후보, 평가 근거, 선택 의도 및 결과 기록

정확한 파일 형식과 저장 스키마는 구현 전 별도로 결정한다.

## 12. 승인된 잠정 설계 9

### 결정 9. 플레이어의 하루 진행 구조

플레이어의 기본 진행 단위는 하루이며, 하루에 하나의 주 행동을 선택한다. 돌발사건에 대한 반응은 주 행동과 별도로 발생할 수 있다.

```text
아침 정보
→ 주 행동 1개
→ 돌발사건 반응
→ NPC 행동 처리
→ 저녁 결과
→ 다음 날
```

#### 아침 정보

플레이어 캐릭터가 직접 관찰했거나 직업·관계·기억·전언을 통해 합리적으로 알고 있는 정보만 보여준다.

- 가족의 굶주림과 건강
- 공동창고에서 업무상 확인할 수 있는 상태
- 전날 직접 겪거나 전해 들은 사건
- 오늘 예상되는 위험과 의무

정보 표시는 결정 7의 정성적 판단 단서 규칙을 따른다. 플레이어가 알지 못하는 객관적 세계 상태는 공개하지 않는다.

#### 하루의 주 행동

플레이어는 하루에 하나의 주 행동을 선택한다. 주 행동은 그날의 주요 시간과 기회를 소비하며, 모든 일을 하루에 수행할 수는 없다.

가뭄 프로토타입의 행동 예시는 다음과 같다.

- 공동창고에서 근무한다.
- 촌장에게 배급 확대를 건의한다.
- 가족의 식량을 구한다.
- 주민의 사정을 조사한다.
- 특정 인물을 찾아간다.
- 창고 경비 상태를 확인한다.
- 마을을 떠날 준비를 한다.

실제 행동 후보는 현재 지식, 위치, 관계, 자원, 의무 및 기회에 따라 생성한다. 실행할 수 없는 행동은 선택지로 제공하지 않는다.

#### 돌발사건 반응

근무 중 절도를 목격하거나, 배우자가 식량을 요구하거나, 주민이 비밀을 알려오는 것처럼 즉시 판단해야 하는 사건은 주 행동과 별개의 반응 선택을 발생시킬 수 있다.

- 반응은 정해진 일일 횟수를 보장하지 않음
- 관련 사건이 없으면 발생하지 않음
- 하나의 사건이 필요 이상의 연속 선택지를 생성하지 않도록 제한함
- 반응 선택도 일반 행동과 같은 실행 가능성 확인 및 결과 처리 경로를 사용함

#### NPC 행동 처리

플레이어의 선택이 처리되는 같은 날에 관련 NPC들도 자신의 정보, 욕구, 관계 및 성향에 따라 행동한다.

- 사건과 관련된 NPC는 상세 판단함
- 그 밖의 NPC는 압축된 일상 처리만 수행함
- 플레이어가 화면에서 보지 않은 행동도 실제로 발생할 수 있음
- 플레이어는 나중에 직접 관찰하거나 정보를 전달받아야 그 행동을 알 수 있음

#### 저녁 결과

정확한 내부 수치나 전지적 결과 요약 대신 플레이어가 관찰하거나 느낄 수 있는 결과만 보여준다.

- 가족이 무엇을 먹었으며 상태가 어떻게 보이는가
- 직접 만난 인물의 태도가 어떻게 달라졌는가
- 어떤 사건이나 소문을 새로 알게 되었는가
- 선택이 어떤 내적 충돌이나 안도감을 남겼는가
- 다음 날 대응해야 할 문제나 기회가 생겼는가

관찰되지 않은 세계 변화는 개발 인과 기록에는 남기되 플레이어 결과 화면에는 표시하지 않는다.

#### 하루 종료와 시간 건너뛰기

- 하루가 끝나면 발생한 사건을 객관적 사건 기록과 인물별 기억 규칙에 따라 기록함
- 게임을 종료하면 단일 연대기 저장에 현재 상태를 반영함
- 즉시 대응할 위기, 의무 또는 돌발사건이 없을 때만 7일 건너뛰기를 허용함
- 건너뛴 기간도 생략하는 것이 아니라 압축 규칙으로 처리함

#### 비범위와 제한

```text
자유 이동 구현 = 하지 않음
실시간 진행 = 하지 않음
행동력 수치 노출 = 하지 않음
하루 주 행동 = 1개
돌발사건 반응 = 필요할 때 추가
플레이어가 모르는 세계 정보 = 표시하지 않음
```

이 구조는 가뭄 프로토타입이 단순 관전형 시뮬레이터가 되지 않도록 하면서도, 이동·시간·행동력 시스템으로 범위가 확장되는 것을 막기 위한 잠정안이다.

## 13. 승인된 잠정 설계 10

### 결정 10. 최소 데이터 구조

가뭄 프로토타입은 트레잇과 캐릭터 유형을 대량으로 먼저 정의하지 않는다. 데이터는 다음 세 층으로 분리한다.

```text
정의 데이터 = 무엇이 존재하고 어떤 의미인가
현재 상태 = 지금 세계와 인물에게 무슨 일이 벌어졌는가
인과 기록 = 왜 그런 판단과 변화가 발생했는가
```

#### 세계 상태

세계 상태에는 최소한 다음 항목을 둔다.

- 현재 날짜와 계절
- 강수 부족과 예상 수확량
- 식량 가격과 공동창고 비축량
- 재현용 난수 시드와 현재 난수 상태
- 플레이어가 조작 중인 인물의 식별자

플레이어 전용 캐릭터 클래스를 만들지 않는다. 일반 인물 중 하나를 `player_person_id`로 지정하며, 플레이어가 조작하지 않을 때는 다른 NPC와 같은 판단 규칙을 적용한다.

#### 인물 상태

모든 60명의 인물은 같은 기본 구조를 사용한다.

```text
신원
가구
직업과 사회적 역할
생존·건강 상태
일반 성향
가치관
현재 감정과 욕구
현재 목표
알고 있는 정보
중요 기억
관계
```

가뭄 프로토타입의 일반 성향은 위험 감수, 공감성, 자기통제 및 규범 중시의 네 가지로 제한한다.

촌장, 창고 관리인 및 농민은 서로 다른 종류의 NPC가 아니라 직업과 권한이 다른 동일한 인간이다. `도둑` 역시 고정된 캐릭터 종류나 영속적 트레잇이 아니라 실제 행동, 기억 및 인물별 평판으로 형성되는 상태다.

#### 가구 상태

식량과 기본 생계는 개인보다 가구 단위로 관리한다.

- 구성원
- 보유 식량
- 재산
- 하루 필요 식량
- 생업
- 부양 부담
- 거주 상태

가족 구성원의 식량을 불필요하게 개인별로 중복 계산하지 않는다. 개인이 숨긴 식량이나 별도 사유재산이 실제로 발생했을 때만 개인 자원으로 기록한다.

#### 관계

관계는 방향성을 가진다.

```text
A가 B를 신뢰하는 정도 ≠ B가 A를 신뢰하는 정도
```

최소 관계 요소는 다음 다섯 가지로 제한한다.

- 신뢰
- 애정
- 두려움
- 원한
- 의무감

60명 전원의 완전한 관계 행렬을 만들지 않는다. 가족, 친구, 이웃, 권력관계 및 갈등처럼 의미 있는 관계만 생성한다. 관계 기록이 없는 두 사람은 기본적으로 중립 또는 미인지 상태로 처리한다.

#### 객관적 사건

실제로 벌어진 사건에는 다음 정보를 기록한다.

- 발생 시점
- 사건 종류
- 실제 행위자와 대상
- 실제 행동과 결과
- 장소 또는 상황
- 목격자
- 공개 여부

객관적 사건 기록은 세계의 진실이지만 NPC의 판단에 직접 사용하지 않는다. 개발 검증과 연대기 생성에 사용하며, NPC는 자신이 가진 정보와 기억을 통해서만 사건에 반응한다.

#### 정보와 믿음

인물별 정보에는 다음 항목을 둔다.

- 무엇이 일어났다는 주장인가
- 현재 보유자는 누구인가
- 직접 목격인가 전언인가
- 최초 정보원과 현재 전달자는 누구인가
- 얼마나 신뢰하는가
- 비밀인가
- 언제 알게 되었는가

같은 사건에 대해 여러 인물이 서로 다른 믿음과 확신을 가질 수 있다.

#### 기억

기억은 객관적 사건의 복사본이 아니라 해당 인물이 받아들인 경험이다.

- 연결된 사건 또는 정보
- 자신이 인식한 행동과 결과
- 관련 인물
- 당시 감정
- 중요도
- 발생 시점
- 최근·중요·핵심 기억 구분

#### 행동과 판단 기록

행동은 다음 세 단계를 분리한다.

```text
행동 정의
→ 특정 인물의 행동 요청
→ 실제 결과와 판단 기록
```

행동 정의에는 실행 조건, 필요한 정보·관계·자원, 판단에 영향을 주는 의미 및 결과 처리 규칙을 둔다.

판단 기록에는 다음을 남긴다.

- 검토한 행동 후보
- 실행할 수 없었던 이유
- 주요 평가 근거
- 선택 당시 의도
- 선택한 행동
- 발생한 결과
- 성향 변화 압력

판단 기록은 개발 검증용이며 플레이어에게 내부 점수를 공개하지 않는다.

#### 복잡도 방지 규칙

```text
NPC 직업별 클래스 상속 = 사용하지 않음
모든 트레잇 사전 제작 = 하지 않음
60×60 완전 관계망 = 만들지 않음
NPC별 실시간 위치 이동 = 계산하지 않음
자유로운 자연어 심리 상태 = 판단에 사용하지 않음
객관적 사건을 NPC가 자동으로 알게 함 = 금지
플레이어 전용 능력치 구조 = 만들지 않음
```

이 구조는 인물을 직업, 신분 또는 최초 성향으로 고정하지 않기 위한 것이다. 촌장도 권력을 잃을 수 있고, 규범적인 주민도 절도를 선택할 수 있으며, 겁이 많았던 인물도 누적된 경험을 통해 변화할 수 있어야 한다.

## 14. 승인된 잠정 설계 11

### 결정 11. 60명 구성과 인물 활성화

주요 NPC와 배경 인물을 영구적인 캐릭터 등급으로 구분하지 않는다. 최초에는 일부 인물만 상세하게 작성하지만, 사건과 관계에 따라 누구든 중심인물로 올라오거나 다시 배경으로 물러날 수 있다.

#### 최초 마을 구성

마을은 총 15가구, 60명으로 구성한다.

| 가구 유형 | 가구 수 | 인원 |
|---|---:|---:|
| 촌장 가구 | 1 | 5 |
| 공동창고 책임자 가구 | 1 | 4 |
| 플레이어 가구 | 1 | 3 |
| 농가 | 8 | 32 |
| 장인·서비스업 가구 | 2 | 7 |
| 여관·교역 가구 | 1 | 5 |
| 토지 없는 빈곤 가구 | 1 | 4 |
| 합계 | 15 | 60 |

이 구성은 사회적 출발점일 뿐 신분을 영구적으로 고정하지 않는다. 가뭄 중에 농민이 경비가 되거나, 부유한 가구가 몰락하거나, 빈곤 가구가 교역으로 성장할 수 있다.

#### 최초 핵심 인물 11명

처음부터 상세한 관계와 기억을 부여할 인물은 다음 11명으로 제한한다.

1. 플레이어 — 공동창고 하급 관리 보조
2. 배우자 — 가족의 생존과 플레이어 선택에 직접 영향
3. 어린 자녀 — 독립된 건강과 굶주림 상태 보유
4. 촌장 — 배급과 마을 통제 권한 보유
5. 공동창고 책임자 — 플레이어의 상급자이자 비축량 접근자
6. 경비 책임자 — 절도 적발과 질서 유지 담당
7. 부유한 농민 겸 곡물 대여자 — 공동창고 외의 식량 권력
8. 빈곤 가구의 가장 — 가장 먼저 생존 압박을 받는 인물
9. 공개적으로 발언하는 주민 — 항의와 집단행동의 연결점
10. 플레이어의 친구 또는 이웃 — 개인적 정보와 소문의 통로
11. 치료사 또는 약초상 — 굶주림·질병·사망 위험을 관찰하는 인물

핵심 인물에게도 선악, 충성, 배신 또는 결말을 미리 확정하지 않는다.

```text
악덕 촌장 = 사전 확정하지 않음
도둑이 될 주민 = 사전 확정하지 않음
반란 지도자 = 사전 확정하지 않음
끝까지 충성할 친구 = 사전 확정하지 않음
```

촌장이 공정한 배급을 할 수도 있고, 빈곤 가구의 가장이 절도 대신 이주를 선택할 수도 있으며, 친구가 플레이어를 고발할 수도 있어야 한다.

#### 나머지 49명

나머지 주민도 이름, 나이, 가구, 생업, 성향, 가치관 및 관계를 가진 완전한 인물 데이터로 존재한다. 다만 장문의 배경 이야기와 전용 사건은 작성하지 않는다.

각 인물에게는 최소한 다음을 부여한다.

- 가구와 직업
- 네 가지 일반 성향
- 가족관계
- 중요한 비가족 관계 최대 3개
- 최초 가치관 1~2개
- 현재 목표 1개
- 최초 자원과 건강 상태

#### 상세 판단 활성화 조건

배경 인물은 다음 조건 중 하나를 만족하면 상세 판단 대상으로 올라온다.

- 플레이어가 직접 접촉함
- 사건의 행위자·대상·목격자가 됨
- 가구의 굶주림이나 건강이 위험 단계에 도달함
- 중요한 정보나 비밀을 알게 됨
- 중요한 관계가 사건으로 변화함
- 현재 목표를 실행할 기회를 얻음

활성화된 인물은 처음부터 핵심 인물이었던 NPC와 같은 행동 판단, 기억 및 정보 규칙을 적용한다.

#### 일일 계산 밀도

```text
60명 전원 = 식량·건강·가구 상태 갱신
평상시 상세 판단 = 약 8~15명
위기 발생 시 = 관련 인물만 일시적으로 확대
영구적인 엑스트라 등급 = 없음
```

`핵심 인물`은 줄거리 보호 대상이 아니라 초기 설계가 상세한 인물이라는 의미뿐이다. 죽거나 떠나거나 영향력을 잃을 수 있다. 반대로 평범했던 주민이 사건을 거치며 마을의 권력자나 플레이어의 숙적이 될 수 있다.

## 15. 승인된 잠정 설계 12

### 결정 12. 가뭄 시작 상태와 초기 갈등

가뭄 시나리오는 위기가 막 시작되는 날이 아니라, 평온한 질서가 무너지기 직전부터 시작한다. 플레이어가 정상적인 규범과 관계가 압박 속에서 변하는 과정을 관찰할 수 있어야 한다.

#### 시나리오 시작 시점

```text
과거 30일 = 의미 있는 비가 거의 오지 않음
수확까지 = 45일
최초 검증 기간 = 60일
작물의 현재 최대 수확 가능량 = 평년의 약 70%
향후 날씨 = 저장된 난수 시드에 따라 결정
이미 발생한 작물 피해 = 비가 와도 완전히 복구되지 않음
```

60일은 강제 게임 종료 시점이 아니라 첫 검증 구간이다. 수확 전 45일과 수확 후 15일을 관찰한다.

#### 식량 단위와 최초 총량

개발 내부에서는 `성인 한 사람이 하루 생존하는 데 필요한 식량`을 1 식량 단위로 사용한다. 정확한 내부 수치는 플레이어에게 공개하지 않는다.

| 자원 | 최초 상태 |
|---|---:|
| 공동창고 장부상 구호용 곡물 | 1,080인분·일 |
| 공동창고 실제 구호용 곡물 | 약 1,026인분·일 |
| 봉인된 종자용 곡물 | 480인분·일 |
| 전체 가구의 사유 식량 합계 | 약 1,440인분·일 |
| 정상적으로 먹을 수 있는 총량 | 약 2,466인분·일 |
| 60명의 45일 필요량 | 약 2,700인분·일 |

현재 식량만으로는 약 4일분이 부족하다. 하지만 교역, 채집, 배급 감축, 이웃 간 공유 또는 종자 사용으로 부족분을 메울 수 있으므로 파국은 확정되지 않는다.

종자용 곡물을 먹으면 당장은 생존하지만 다음 파종과 장기 생존 가능성이 악화된다.

#### 가구별 불균형

총량보다 분배 차이가 먼저 문제를 일으킨다.

```text
부유한 농가 = 해당 가구 기준 약 70일분
일반 가구 = 약 8~35일분
플레이어 가구 = 약 10일분
빈곤 가구 = 약 3일분
```

부유한 농가의 곡물은 공동체 자원이 아니다. 촌장은 요청, 차용, 매입 또는 징발할 수 있지만 각각 관계, 정당성 또는 강제력 비용이 발생한다.

#### 공동창고의 장부 차이

장부상 구호용 곡물과 실제 곡물 사이에는 약 5% 차이가 있다.

- 최초 원인은 부패나 절도로 확정하지 않음
- 건조 손실, 쥐, 계량 오류 및 기록 누락이 복합된 결과
- 촌장과 창고 책임자는 장부상 수량만 알고 있음
- 플레이어는 업무 중 실사를 선택하면 차이를 발견할 수 있음
- 차이가 알려지면 주민들은 횡령이나 은폐로 오해할 수 있음

이 차이는 사건의 원인이 될 수 있지만 반드시 밝혀지거나 정치적 갈등으로 이어지는 것은 아니다.

#### 최초 정보 격차

| 인물 | 알고 있는 정보 |
|---|---|
| 촌장 | 장부상 비축량, 세금과 종자 의무 |
| 창고 책임자 | 장부 기록과 입출고 내역 |
| 플레이어 | 대략적인 장부와 창고의 현장 상태 |
| 부유한 농민 | 자신의 실제 비축량과 거래 가능량 |
| 일반 주민 | 가뭄 징후와 자기 가구의 식량 |
| 치료사 | 굶주림과 건강 악화가 시작된 가구 |
| 여관·교역 가구 | 외부 식량 가격과 상인의 방문 가능성 |

누구도 마을 전체의 정확한 식량 상태를 알지 못한다.

#### 최초 관계 압력

정확한 수치 대신 다음 방향을 고정한다.

- 플레이어는 촌장을 비교적 신뢰함
- 촌장은 플레이어를 성실하지만 권한 없는 하급자로 봄
- 플레이어와 배우자의 애정과 의무감은 높음
- 배우자는 촌장보다 가족의 생존을 우선함
- 촌장과 창고 책임자의 업무상 신뢰는 높음
- 창고 책임자는 규칙 위반과 책임 추궁을 두려워함
- 촌장은 지난겨울 부유한 농민에게 곡물을 빌린 의무가 있음
- 빈곤 가구의 가장은 촌장에게 아직 적대적이지 않지만 불안이 큼
- 공개 발언자는 배급 불공정을 의심하지만 증거는 없음
- 플레이어의 친구는 플레이어와 경비 책임자 양쪽과 관계가 있음

#### 상태 기반 사건 트리거

사건은 특정 날짜에 강제로 발생하지 않는다.

| 조건 | 생성 가능한 상황 |
|---|---|
| 가구 식량이 3일 이하 | 도움 요청, 차용, 절도, 이주 검토 |
| 여러 가구가 7일 이하 | 배급 논의, 항의, 식량 공유 |
| 창고 차이 발견 | 실사, 보고, 은폐, 소문 |
| 종자 사용 논의 | 단기 생존과 다음 농사의 충돌 |
| 사유 곡물 소유자가 확인됨 | 거래, 청원, 압박, 징발 |
| 건강 악화 목격 | 치료 요청, 가족 갈등, 배급 우선순위 논쟁 |
| 외부 상인 정보 입수 | 구매, 빚, 호송 또는 사기 위험 |

트리거는 선택 기회만 만든다. 촌장의 거절, 주민의 절도, 폭동 또는 플레이어의 배신을 확정하지 않는다.

#### 고정하지 않을 결과

```text
촌장의 배급 결정 = 미확정
창고 부족분의 정치적 책임 = 미확정
부유한 농민의 협조 여부 = 미확정
빈곤 가구의 절도 여부 = 미확정
플레이어의 규범 변화 = 미확정
수확 전 사망자 발생 = 미확정
마을의 생존 또는 붕괴 = 미확정
```

초기 식량은 충분하지 않지만 즉시 전멸을 강제할 정도로 부족하지도 않다. 공정한 협력으로 피해를 줄일 수 있지만, 불신, 오판 및 사적 이익으로 같은 자원을 가진 마을이 붕괴할 수도 있어야 한다.

## 16. 승인된 잠정 설계 13

### 결정 13. 핵심 인물 초기 프로필

핵심 인물은 선악이나 직업 유형으로 고정하지 않고, 서로 충돌할 수 있는 성향과 가치관을 배치한다.

#### 고정된 기준 프로필

첫 프로토타입은 시작할 때마다 인물 성향을 무작위로 생성하지 않는다.

```text
REFERENCE CAST = A
INITIAL PROFILES = FIXED
TRAIT VALUES = HIDDEN FROM PLAYER
RANDOMIZED PERSONALITIES = NOT USED
```

먼저 동일한 초기 인물로 인과를 재현한다. 시스템이 검증된 뒤에만 다른 인물 구성과 무작위 생성을 시험한다.

#### 가뭄 프로토타입의 가치관

일반 성향 네 가지와 별도로 다음 여섯 가치관만 사용한다.

| 가치관 | 판단에 미치는 영향 |
|---|---|
| 가족 보호 | 자기 가구의 생존과 안전을 우선함 |
| 공동체 생존 | 마을 전체와 장기 존속을 고려함 |
| 정당한 질서 | 규칙, 직무, 합법적 권위를 중시함 |
| 공정과 호혜 | 공평한 부담, 보답과 상호부조를 중시함 |
| 재산 자율 | 사유재산과 강제 징발에 대한 저항 |
| 생명 보호 | 질병·굶주림·사망 방지를 우선함 |

가치관 역시 `0~100`의 숨겨진 내부 수치를 가지며 경험에 따라 천천히 변할 수 있다.

#### 핵심 인물 11명의 성향

| 인물 | 위험 감수 | 공감성 | 자기통제 | 규범 중시 | 지배적 가치관 |
|---|---:|---:|---:|---:|---|
| 플레이어 | 36 | 64 | 74 | 78 | 가족 보호 84, 정당한 질서 76 |
| 배우자 | 44 | 68 | 62 | 57 | 가족 보호 92, 공정과 호혜 62 |
| 어린 자녀 | 58 | 55 | 28 | 35 | 가족 보호 85 |
| 촌장 | 43 | 60 | 76 | 72 | 공동체 생존 85, 정당한 질서 82 |
| 창고 책임자 | 27 | 50 | 82 | 86 | 정당한 질서 88, 가족 보호 64 |
| 경비 책임자 | 62 | 46 | 69 | 74 | 정당한 질서 84, 공동체 생존 60 |
| 부유한 농민 | 49 | 53 | 79 | 63 | 재산 자율 88, 가족 보호 84 |
| 빈곤 가구의 가장 | 54 | 67 | 56 | 69 | 가족 보호 94, 공정과 호혜 74 |
| 공개 발언자 | 69 | 73 | 52 | 49 | 공정과 호혜 90, 공동체 생존 82 |
| 친구·이웃 | 53 | 61 | 57 | 59 | 공정과 호혜 78, 가족 보호 72 |
| 치료사·약초상 | 37 | 84 | 75 | 66 | 생명 보호 94, 공동체 생존 80 |

극단적인 `0`이나 `100`은 사용하지 않는다. 어느 인물도 한 가지 반응만 반복하도록 만들지 않기 위해서다.

어린 자녀도 같은 인물 구조를 사용하지만 나이 때문에 생성되는 행동 후보가 제한된다.

#### 최초 목표

각 인물은 장문의 행동 계획 대신 현재 목표 하나만 가진다.

| 인물 | 최초 목표 |
|---|---|
| 플레이어 | 창고 업무를 지키면서 가족의 식량을 확보함 |
| 배우자 | 가구가 수확기까지 버틸 방법을 찾음 |
| 어린 자녀 | 부모 곁에서 안전과 돌봄을 구함 |
| 촌장 | 식량 상황을 파악하고 수확기까지 질서를 유지함 |
| 창고 책임자 | 책임 추궁을 피하면서 장부와 창고를 보존함 |
| 경비 책임자 | 공동창고를 지키고 소요를 예방함 |
| 부유한 농민 | 가족의 곡물을 보존하고 기존 채권을 보호함 |
| 빈곤 가구의 가장 | 존엄을 잃지 않고 가족의 식량을 구함 |
| 공개 발언자 | 배급 불공정 의혹을 확인하고 공개 기준을 요구함 |
| 친구·이웃 | 자기 가구를 지키면서 플레이어와의 관계를 유지함 |
| 치료사·약초상 | 굶주림이 심해지는 가구를 찾아 생명 피해를 막음 |

목표는 행동을 강제하지 않는다. 현재 상태와 경험에 따라 변경될 수 있다.

#### 핵심 관계 기준값

관계 수치는 `0~100`의 숨겨진 내부 값이다. 아래 표의 숫자는 `앞 인물→뒤 인물 / 뒤 인물→앞 인물` 순서다.

| 관계 | 신뢰 | 애정 | 두려움 | 원한 | 의무감 |
|---|---:|---:|---:|---:|---:|
| 플레이어 ↔ 배우자 | 88 / 84 | 92 / 90 | 0 / 0 | 0 / 0 | 88 / 82 |
| 플레이어 ↔ 자녀 | 92 / 86 | 96 / 94 | 0 / 5 | 0 / 0 | 98 / 20 |
| 플레이어 ↔ 촌장 | 68 / 56 | 12 / 8 | 10 / 0 | 0 / 0 | 58 / 22 |
| 플레이어 ↔ 창고 책임자 | 62 / 60 | 15 / 12 | 18 / 0 | 0 / 0 | 72 / 42 |
| 촌장 ↔ 창고 책임자 | 72 / 74 | 12 / 10 | 0 / 30 | 0 / 0 | 55 / 84 |
| 촌장 ↔ 경비 책임자 | 64 / 69 | 10 / 10 | 0 / 18 | 0 / 0 | 52 / 82 |
| 촌장 ↔ 부유한 농민 | 54 / 47 | 8 / 5 | 8 / 12 | 0 / 0 | 68 / 45 |
| 촌장 ↔ 빈곤 가구 가장 | 40 / 43 | 5 / 5 | 0 / 22 | 0 / 8 | 45 / 15 |
| 촌장 ↔ 공개 발언자 | 40 / 34 | 3 / 5 | 10 / 15 | 5 / 14 | 25 / 8 |
| 플레이어 ↔ 친구 | 76 / 74 | 64 / 62 | 0 / 0 | 0 / 0 | 42 / 40 |
| 친구 ↔ 경비 책임자 | 55 / 50 | 20 / 18 | 8 / 5 | 0 / 0 | 18 / 24 |

표에 없는 관계는 가족과 직업상 필요한 연결만 추가하며, 나머지는 중립 또는 미인지 상태로 시작한다.

#### 최초 감정 상태

모두 전날까지는 식사를 했으므로 굶주림과 죄책감은 낮게 시작한다.

- 플레이어: 약한 불안
- 배우자: 가족 식량에 대한 중간 수준의 공포
- 촌장: 작황에 대한 약한 공포
- 창고 책임자: 책임 추궁에 대한 중간 수준의 공포
- 빈곤 가구 가장: 높은 공포와 약한 분노
- 공개 발언자: 약한 공포와 중간 이하의 분노
- 나머지 인물: 낮은 공포와 분노

빈곤 가구도 처음부터 절도 직전 상태로 두지 않는다. 도움 요청이나 차용 같은 합법적 수단을 먼저 선택할 가능성이 충분해야 한다.

#### 의도한 내부 충돌

```text
플레이어 = 가족 보호 ↔ 규범과 직무
촌장 = 공동체 생존 ↔ 질서와 권력 유지
창고 책임자 = 정확한 보고 ↔ 책임 회피
경비 책임자 = 질서 유지 ↔ 굶주린 주민에 대한 판단
부유한 농민 = 재산권과 가족 ↔ 공동체의 생존
빈곤 가구 가장 = 높은 규범 의식 ↔ 가족의 절박함
공개 발언자 = 공정성 추구 ↔ 처벌 위험
치료사 = 생명 보호 ↔ 제한된 식량과 약품
```

부유한 농민도 자발적으로 곡물을 나눌 수 있고, 공감성이 높은 공개 발언자도 위험한 군중행동을 촉발할 수 있다. 초기 프로필은 결말이 아니라 서로 다른 결정을 만들어낼 압력의 배치다.

## 17. 승인된 잠정 설계 14

### 결정 14. 행동 후보와 효용 평가

가뭄 프로토타입은 복잡한 행동 트리 대신 실행 가능한 행동만 생성하고, 인물이 알고 있다고 믿는 결과를 기준으로 비교한다.

#### 행동 정의 구조

모든 행동은 다음 정보를 가진다.

```text
행동 ID
표시 이름
실행 조건
가능한 대상
의도 후보
가치관·규범 의미
인식 가능한 위험
예상 결과 계산법
실제 결과 처리기
목격·정보 생성 규칙
시간과 기회 비용
```

행동의 예상 결과와 실제 결과는 분리한다. NPC가 성공할 것으로 믿고 행동했더라도 실제로 실패할 수 있다.

#### 최초 행동군

| ID | 행동군 | 예시 |
|---|---|---|
| A00 | 현재 행동 유지 | 근무 지속, 기다림, 기존 계획 유지 |
| A01 | 노동·식량 확보 | 품삯 노동, 채집, 사냥 보조 |
| A02 | 조사·실사 | 창고 확인, 장부 대조, 작황 조사 |
| A03 | 정보 활동 | 사람을 만남, 질문, 보고, 소문 전달 |
| A04 | 도움 요청 | 배우자·이웃·촌장에게 식량을 요청 |
| A05 | 협상·거래 | 구매, 차용, 물물교환, 조건부 합의 |
| A06 | 제공·공유 | 증여, 대여, 공동배급 참여 |
| A07 | 희소 자원 배분 | 가족 중 누구에게 얼마나 먹일지 결정 |
| A08 | 설득·조직 | 배급 건의, 주민 설득, 공개 항의 |
| A09 | 보호·개입 | 창고 경비, 싸움 중재, 피해자 보호 |
| A10 | 통제·징발 | 출입 제한, 구금, 재산 압수 |
| A11 | 절도·무단침입 | 곡물 절도, 봉인 해제, 몰래 조사 |
| A12 | 정보 보류·은폐 | 보고 연기, 침묵, 증거 감춤 |
| A13 | 이주 준비·실행 | 식량 마련, 가족 설득, 마을 이탈 |

A00은 항상 존재하는 최종 대안이다. 다른 행동의 기대효용이 모두 낮으면 NPC는 현재 행동을 유지한다.

첫 프로토타입에서는 다음을 제외한다.

```text
의도적인 거짓말 = 제외
살인·전투 행동 = 제외
자유 형식 행동 생성 = 제외
LLM 행동 제안 = 제외
직업별 전용 행동 시스템 = 제외
```

#### 행동 후보 생성

NPC가 모든 행동군을 매일 평가하지 않는다. 실행 조건을 만족하는 행동만 후보가 된다.

예를 들어 절도에는 최소한 다음 조건이 필요하다.

- 훔칠 식량의 존재를 알고 있거나 믿음
- 대상이나 장소에 접근할 방법이 있음
- 감시가 약한 기회를 알고 있거나 추정함
- 식량 획득이 현재 목표와 관련 있음

부유한 농민의 곡물 존재를 모르는 주민에게는 해당 농가의 곡물을 훔치는 선택지가 생성되지 않는다.

#### 효용 평가 공식

각 요소는 다음 내부 범위를 사용한다.

```text
N = 현재 욕구 완화                  -100~100
G = 현재 목표 부합                  -100~100
V = 가치관·성향 부합                -100~100
R = 관계에 미칠 것으로 믿는 영향    -100~100
M = 예상 자원·건강·지위 변화        -100~100
K = 인식한 위험 비용                   0~100
C = 규범·직무 충돌                     0~100
T = 시간·기회·계획 변경 비용           0~100
```

최초 공식은 다음으로 고정한다.

```text
U = 0.30N + 0.20G + 0.20V + 0.10R + 0.10M
    - 0.15K - 0.15C - 0.05T
```

효용 수치는 플레이어에게 공개하지 않는다.

#### 욕구 완화

굶주림, 질병 및 안전 위협이 낮을 때는 영향이 작고 위험 단계에 가까워질수록 가파르게 커진다.

```text
욕구 긴급도 = 선형 증가가 아니라 제곱 곡선 사용
```

식량이 20일 남은 인물과 오늘 가족이 굶는 인물은 같은 식량 획득 행동을 전혀 다르게 평가한다.

#### 위험 비용

위험 감수 성향이 높아도 위험이 완전히 사라지지는 않는다.

```text
K = 인식한 위험
  × (1 - 0.006 × 위험 감수)
  × (1 + 0.005 × 현재 공포)
```

결과는 `0~100`으로 제한한다. NPC가 경비 증원을 모르면 실제 위험이 높더라도 평가에는 반영하지 않는다.

#### 규범·직무 충돌

```text
C =
0.6 × 일반 규범 위반도 × (0.25 + 0.0075 × 규범 중시)
+
0.4 × 직무 위반도 × 정당한 질서 가치 / 100
```

규범 중시가 낮아도 절도와 같은 규범 위반에 대한 최소한의 심리적 비용은 남는다. 창고 직원인 플레이어는 일반 주민보다 창고 절도에서 더 큰 직무 충돌을 겪는다.

#### 가치관 부합

행동이 가진 의미와 인물의 가치관을 비교한다.

`공동창고에서 곡물을 훔쳐 자녀에게 먹인다`는 행동은 동시에 다음 의미를 가질 수 있다.

```text
가족 보호 = 강한 부합
정당한 질서 = 강한 충돌
재산 자율 = 충돌
생명 보호 = 부합
```

한 행동을 하나의 가치관으로만 판정하지 않는다.

#### 관계 영향

행동으로 직접 영향을 받을 인물 중 가장 중요한 세 명까지만 평가한다.

- 애정과 의무감이 높은 사람의 이익은 긍정적으로 평가함
- 신뢰하는 사람을 배신하면 부정적으로 평가함
- 원한이 있는 사람의 손실은 긍정적으로 느낄 수도 있음
- 발각되지 않을 것으로 믿으면 사회적 관계 손실을 낮게 예상함

#### 불확실한 정보

전언이나 소문을 바탕으로 한 예상 이익은 정보 신뢰도만큼 축소한다. 불확실성 자체를 별도의 무작위 왜곡으로 만들지 않는다.

#### NPC의 최종 선택

1. 실행 가능한 후보만 생성한다.
2. 각 후보의 기본 효용을 계산한다.
3. 최고 점수가 `0` 이하이면 A00을 선택한다.
4. 최고 후보가 차순위보다 5점 이상 높으면 그대로 선택한다.
5. 차이가 5점 미만일 때만 제한된 난수로 결정한다.

난수는 전체 NPC가 공유하는 순차 난수에 의존하지 않는다.

```text
결정 난수 =
세계 시드
+ 날짜
+ 행위자 ID
+ 결정 ID
+ 행동 ID
```

따라서 무관한 NPC 한 명이 추가로 활성화됐다는 이유만으로 다른 인물의 모든 선택 결과가 뒤집히지 않는다.

#### 플레이어의 선택과 의도

플레이어는 실행 가능한 행동 중 직접 선택하므로 효용 최고 행동을 강제하지 않는다.

성향에 크게 어긋나는 행동도 선택할 수 있다. 다만 결정 7에 따라 내적 충돌과 인식 가능한 위험을 정성적으로 표시한다.

하나의 행동에 여러 의도가 가능하고 그것이 결과나 성향 변화에 영향을 줄 때만 의도 선택을 추가한다.

```text
공동창고의 곡물을 훔친다.

가능한 의도:
- 가족을 살리기 위해
- 자신의 몫을 확보하기 위해
- 촌장에게 보복하기 위해
```

- 현재 상태로 성립 가능한 의도만 표시함
- 최대 3개만 표시함
- 한 가지 의도만 가능하면 자동으로 기록함
- 의도 선택은 별도의 하루 행동으로 계산하지 않음

NPC는 효용 계산에서 가장 크게 기여한 목표나 가치관을 의도로 기록한다.

#### 판단 기록

개발 기록에는 다음 형태로 남긴다.

```text
행위자 = 빈곤 가구 가장
결정 = DAY_03_FOOD_RESPONSE

도움 요청 = 46.8
절도 = 30.8
이주 준비 = 18.1
현재 상태 유지 = 0.0

선택 = 도움 요청
주요 의도 = 가족 보호
주요 근거 = 식량 3일, 높은 규범 중시, 촌장에게 도움을 요청할 수 있음
```

이후 도움을 거절당하고 가족이 굶으면 같은 인물이 다음 판단에서 절도를 더 높게 평가할 수 있다. 이것은 별도의 절도 이벤트가 강제로 발생해서가 아니라 욕구, 신뢰, 분노 및 예상 이익이 변했기 때문이다.

#### 선택과 성향 변화의 분리

효용 점수가 높았다는 이유만으로 성향이 변하지 않는다. 행동 후 변화 압력은 다음을 기준으로 별도 계산한다.

- 자발적으로 선택했는가
- 기존 성향과 얼마나 충돌했는가
- 위험과 비용을 사전에 알고 있었는가
- 실제 결과를 직접 경험했는가
- 자신의 책임이라고 인식하는가
- 같은 행동을 반복하고 있는가

따라서 절도에 성공했다고 자동으로 규범 중시가 크게 낮아지지는 않는다. 죄책감, 자기합리화, 가족의 생존, 발각 여부 및 반복 경험이 함께 작동해야 한다.

행동 선택과 실제 성공·실패 판정은 분리한다. 실제 결과 계산은 후속 설계에서 정한다.

## 18. 승인된 잠정 설계 15

### 결정 15. 행동 실행과 실제 결과

모든 행동을 하나의 성공 확률로 처리하지 않는다. 거래와 요청은 상대 NPC의 판단으로 처리하고, 절도와 조사처럼 불확실한 행동만 상황 계산으로 판정한다.

#### 결과 처리 원칙

```text
선택한 행동 ≠ 성공한 행동
높은 효용 ≠ 높은 성공 확률
사회적 설득 ≠ 매력 능력치 판정
물리적 성공 ≠ 발각되지 않음
```

결과는 다음 묶음으로 기록한다.

```text
주요 목적 달성 정도
실제 자원·건강 변화
시간과 기회 비용
발각·목격·증거
관계와 의무 변화
생성된 객관적 사건
인물별 정보와 기억
감정 및 성향 변화 압력
```

#### 실행 직전 재검증

행동을 선택한 뒤 세계 상태가 바뀌었을 수 있으므로 실행 직전에 조건을 다시 확인한다.

- 대상이 여전히 존재하는가
- 필요한 자원이 남아 있는가
- 접근 권한이나 기회가 유지되는가
- 대상이 떠나거나 사망하지 않았는가
- 같은 자원을 다른 행동이 먼저 차지하지 않았는가

NPC의 행동이 불가능해지면 남아 있는 후보 중 차순위를 다시 검토한다. 플레이어 행동이 불가능해지면 그 이유를 보여주고 가능한 대응을 다시 선택하게 한다.

#### 결과 판정 유형

| 유형 | 처리 방식 | 예시 |
|---|---|---|
| R0 확정 처리 | 조건이 충족되면 그대로 실행 | 자기 식량을 가족에게 배분 |
| R1 상대방 판단 | 상대 NPC가 자신의 효용으로 응답 | 도움 요청, 거래, 설득 |
| R2 불확실한 과업 | 상황상 이점과 난도를 비교 | 실사, 채집, 장부 조사 |
| R3 대항 행동 | 행동자와 방해자의 조건을 비교 | 절도, 징발, 경비 돌파 |
| R4 지속 행동 | 여러 날의 준비와 누적 상태로 처리 | 이주 준비, 장기 조사 |

행동군마다 하나 이상의 판정 유형을 지정한다.

#### 사회적 행동은 상대 NPC가 결정

도움 요청, 거래, 협상 및 설득에는 단순 성공 확률을 사용하지 않는다.

```text
플레이어가 식량을 요청함
→ 상대가 요청과 조건을 인식함
→ 상대에게 응답 행동 후보 생성
→ 상대의 성향·가치관·관계·자원으로 평가
→ 수락 / 일부 수락 / 조건 제시 / 거절
```

높은 신뢰는 상대의 판단에 유리하지만 상대의 결정을 강제로 빼앗지 않는다.

부유한 농민은 플레이어를 좋아하더라도 가족의 식량이 부족하면 거절할 수 있고, 싫어하는 사람에게도 충분한 대가가 제시되면 판매할 수 있다.

#### 불확실·대항 행동 계산

새로운 힘, 민첩 또는 화술 능력치는 만들지 않는다. 기존 정보에서 상황상 이점과 저항을 계산한다.

행동 측 이점은 다음에서 가져온다.

- 직업과 역할에서 얻은 경험
- 대상에 관한 지식
- 사전 준비
- 접근 권한과 기회
- 도구와 자원
- 협력자
- 현재 건강과 감정 상태

저항 측 요소는 다음에서 가져온다.

- 과업 자체의 난도
- 대상의 저항
- 경비와 감시
- 장소의 보안
- 시간 부족
- 건강 악화
- 경쟁하는 다른 행동

각 행동 정의는 관련 요소를 최대 4개씩 선택하고 가중치 합계를 `1.0`으로 맞춘다.

```text
P = 행동 측 이점의 가중평균       0~100
D = 저항 측 요소의 가중평균       0~100
J = 제한 난수                    -5~5

결과 여유 M = P - D + J
```

`P-D`의 절댓값이 20 이상이면 난수 `J`를 사용하지 않는다. 결과가 분명한 상황은 운으로 뒤집히지 않는다.

#### 결과 단계

| 결과 여유 | 판정 |
|---:|---|
| 20 이상 | 목적 완전 달성 |
| 5~19 | 부분 달성 |
| -4~4 | 교착 또는 불확실한 진전 |
| -19~-5 | 실패 |
| -20 이하 | 명백한 실패 |

명백한 실패라고 해서 자동으로 치명상이나 체포가 발생하지 않는다. 추가 피해는 해당 행동에 원래 존재하는 위험이 실제로 발생했을 때만 적용한다.

각 행동은 단계별 결과를 별도로 정의한다.

```text
창고 실사 완전 달성 = 실제 부족량과 가능한 원인을 확인
창고 실사 부분 달성 = 장부와 실물이 맞지 않는다는 사실만 확인
창고 실사 교착 = 일부 기록이 이상하지만 확신하지 못함
창고 실사 실패 = 의미 있는 차이를 발견하지 못함
```

#### 성공과 발각의 분리

은밀한 행동은 목적 달성과 노출 여부를 따로 판정한다.

```text
절도 성공 + 미발각
절도 성공 + 목격됨
절도 실패 + 흔적이 남음
절도 실패 + 아무도 모름
```

노출 판정에는 다음을 사용한다.

- 행동 자체의 가시성
- 장소와 시간
- 직접 목격자
- 경비 상태
- 남겨진 흔적
- 사전 준비와 은폐
- 목격자의 주의와 정보

직접 목격자가 있으면 객관적인 목격 정보가 생성된다. 흔적만 발견되면 `누군가 곡물을 건드렸다`는 정보는 생기지만 범인이 자동으로 알려지지는 않는다.

#### 하루의 처리 순서

시간 단위를 세분화하지 않고 행동에 추상적인 실행 단계만 부여한다.

```text
1. 아침 공공·행정 행동
2. 주간 노동·조사·거래
3. 사회적 요청과 상대방 판단
4. 야간 은밀 행동
5. 식량 소비와 건강 갱신
6. 사건·기억·관계·성향 압력 정리
```

같은 자원을 여러 사람이 노리면 하나의 충돌 집단으로 묶어 처리한다. NPC 배열 순서가 빠르다는 이유로 자원을 먼저 차지하지 않는다.

#### 반응 연쇄 제한

하나의 행동이 새로운 반응을 계속 생성하면 계산과 사건이 폭발할 수 있다.

```text
원 사건
→ 직접 관계자의 즉시 반응 1회
→ 추가 결과는 다음 날 판단으로 이월
```

첫 프로토타입에서는 하나의 사건당 즉시 반응 단계를 한 번만 허용한다. 다만 객관적 사건, 목격 정보 및 관계 변화는 모두 남으므로 다음 날 새로운 행동으로 이어질 수 있다.

#### 결과 적용 순서

```text
실행 조건 재검증
→ 상대방 판단 또는 과업 판정
→ 주요 결과 확정
→ 발각·목격 판정
→ 자원·건강·의무 변경
→ 객관적 사건 기록
→ 목격자별 정보 생성
→ 관계·감정·기억 변경
→ 성향 변화 압력 기록
→ 다음 날 반응 후보 생성
```

관계와 평판은 사건을 알게 된 인물에게만 적용한다. 객관적 사건 기록을 모든 NPC가 자동으로 참조하지 않는다.

#### 절도 예시

플레이어가 야간에 공동창고 곡물 12단위를 훔치려 한다고 가정한다.

```text
행동 측 이점:
- 창고 접근 권한
- 내부 구조에 대한 지식
- 경비 시간 확인
- 사전 준비

저항 측 요소:
- 자물쇠
- 경비 책임자의 순찰
- 운반해야 할 곡물의 양
- 흔적이 남을 가능성
```

부분 달성이라면 12단위 전부가 아니라 일부만 가져갈 수 있다. 이후 발각 판정에서 직접 목격자는 없지만 자루 위치가 달라졌다는 흔적이 남을 수 있다.

```text
식량 획득 = 6
직접 목격자 = 없음
창고 흔적 = 있음
플레이어의 기억 = 절도와 가족 보호 의도
다음 날 경비 책임자 = 이상 징후 조사 가능
일반 주민 = 아직 사건을 모름
```

경비 책임자가 조사하지 않거나 실패하면 범인이 끝까지 드러나지 않을 수도 있다.

#### 난수 재현

결과 난수도 결정 난수와 마찬가지로 독립적으로 생성한다.

```text
결과 난수 =
세계 시드
+ 날짜
+ 행동 인스턴스 ID
+ 행위자 ID
+ 대상 ID
+ 판정 종류
```

무관한 NPC의 행동 수나 내부 처리 순서가 바뀌어도 동일한 행동 조건에서는 동일한 결과가 나와야 한다.

이 구조는 성공과 실패를 단순 주사위로 만들지 않으면서도 불확실성을 남긴다. 특히 사회적 행동에서 상대 NPC의 선택권을 보존한다.

## 19. 승인된 잠정 설계 16

### 결정 16. 검증 시나리오와 판정표

가뭄 프로토타입은 특정 줄거리가 나오는지가 아니라 인과 시스템이 실제로 작동하는지를 반증 가능한 시험으로 검증한다.

#### 검증 원칙

```text
정해진 결말 재현 = 검증 목표 아님
같은 조건의 재현성 = 필수
한 조건만 바꾼 인과 차이 = 필수
판단 이유 역추적 = 필수
테스트 전용 예외 코드 = 금지
```

모든 테스트는 실제 게임과 같은 행동 생성, 효용 계산 및 결과 처리 경로를 사용한다.

#### 검증용 실행 방식

플레이어를 사람이 조작하지 않는 시험에서는 플레이어 캐릭터도 동일한 NPC 판단 규칙으로 움직인다.

```text
REFERENCE CAST = A
PRIMARY TEST SEED = 1001
ADDITIONAL SEEDS = 1002, 1003
TEST HORIZON = 60 DAYS
```

다른 시드는 재현 불가능한 무작위성을 만들기 위한 것이 아니라 제한 난수와 날씨 분기를 검사하기 위한 것이다.

#### 필수 기록물

각 검증 실행은 다음을 남긴다.

- 날짜별 세계 상태 해시
- 모든 상세 판단 후보와 점수
- 선택 행동과 의도
- 실제 결과와 발각 결과
- 객관적 사건 기록
- 인물별 정보 전달 경로
- 기억 생성, 압축 및 삭제
- 관계와 성향 변화 압력
- 주간 성향 정리 결과
- 60일 종료 상태 요약

상태 해시는 인물, 가구, 관계 및 정보를 ID 순으로 정렬한 표준 상태에서 계산한다.

#### 기계적 불변조건 시험

| ID | 시험 | 합격 기준 |
|---|---|---|
| I01 | 동일 상태·동일 시드 재실행 | 날짜별 상태 해시 완전 일치 |
| I02 | NPC 저장 순서 변경 | 행동과 결과가 기존 실행과 일치 |
| I03 | 저장 후 재개 | 중단 없이 실행한 결과와 최종 해시 일치 |
| I04 | 자원 보존 | 생성·소비·이전 근거 없는 식량 증감 0건 |
| I05 | 실행 조건 | 불가능한 행동이 실제 실행된 사례 0건 |
| I06 | 정보 경계 | 사건을 모르는 NPC의 직접 반응 0건 |
| I07 | 반응 깊이 | 하나의 사건에서 즉시 반응 1회를 초과한 사례 0건 |
| I08 | 기억 한도 | 최근·중요·핵심 기억 상한 위반 0건 |
| I09 | 성향 변화 한도 | 주간 최대 변화와 반복 감소 규칙 위반 0건 |
| I10 | 플레이어 단서 | 선택당 3개 초과 또는 전지적 단서 제공 0건 |

I01~I10 중 하나라도 실패하면 프로토타입은 합격할 수 없다.

#### C01 — 합법적 수단이 있는 상태 관찰

초기 빈곤 가구 가장에게 다음 조건을 준다.

```text
가구 식량 = 3일
촌장에게 도움 요청 가능
창고 식량 존재를 알고 있음
절도 기회도 알고 있음
```

관찰 항목은 다음과 같다.

- 도움 요청이 후보에 존재함
- 절도도 조건이 충족되면 후보에 존재함
- 각 후보의 N, G, V, R, M, K, C, T와 총효용
- 최종 선택과 감사 가능한 계산 근거

어느 후보가 더 높아야 한다는 방향은 지정하지 않는다.

#### C02 — 경험에 따른 판단 변화

C01 이후 다음 상태를 적용한다.

```text
도움 요청 = 거절됨
가구 식량 = 0일
가족 건강 = 악화
촌장 신뢰 = 하락
분노 = 상승
낮은 경비 기회 = 인식함
```

관찰 항목은 다음과 같다.

- C01과 비교한 모든 후보·구성요소·총효용의 변화
- 요청 거절 기억과 변경된 주관적 정보가 실제 계산 입력에 포함됐는지 여부
- 최종 선택과 C01 대비 선택 변화 여부

절도 효용이나 특정 구성요소가 반드시 상승해야 한다고 규정하지 않는다. 변경 입력이 동결된 정의에 따라 계산에 반영됐는지만 기계적으로 확인한다.

#### C03 — 도움을 받은 반대 조건

C01에서 촌장이 충분한 식량을 제공한다.

관찰 항목은 다음과 같다.

- C01·C02와 비교한 후보·구성요소·총효용
- 도움 제공이 입력에 반영된 방식
- 최종 선택

도움을 받으면 절도 압력이 반드시 감소해야 한다는 방향은 지정하지 않는다.

#### C04 — 부양가족 반대 조건

플레이어에게 자녀가 없고 자기 식량만 부족한 별도 시험 상태를 만든다.

관찰 항목은 다음과 같다.

- 부양가족 유무 외의 입력이 동일한지 여부
- 가족 보호와 관련된 정의가 구성요소 계산에 반영된 방식
- 후보·구성요소·총효용·최종 선택의 차이

절도 효용이 반드시 낮아져야 한다는 방향은 지정하지 않는다.

#### C05 — 알고 있는 위험과 실제 위험

세 가지 상태를 비교한다.

```text
A = 경비가 약하고 인물도 그렇게 알고 있음
B = 경비가 강하고 인물도 알고 있음
C = 경비가 강하지만 인물은 약하다고 믿음
```

기계적 확인과 관찰 항목은 다음과 같다.

- 알려지지 않은 실제 경비만 다른 A와 C의 판단 입력·후보·점수·선택은 동일함
- 알려진 경비가 다른 B는 동결된 정의에 따라 다시 계산됨
- C의 NPC가 실제 경비 정보를 몰래 참조하지 않음
- B의 재계산 결과와 최종 선택은 방향을 지정하지 않고 기록함

행동 결과에서 실제 경비를 적용하는 시험은 M4 범위다.

#### C06 — 사회적 행동의 상대방 자율성

같은 인물이 같은 조건으로 두 명에게 곡물을 요청한다.

- 한 명은 식량이 충분하고 공감성이 높음
- 다른 한 명은 식량이 부족하고 가족 보호가 높음

합격 기준은 다음과 같다.

- 요청자가 높은 능력치로 상대를 강제하지 않음
- 각 상대가 자신의 효용으로 별도 판단함
- 수락, 일부 수락, 조건부 제시 또는 거절이 응답 행동으로 기록됨

#### C07 — 성공과 발각 분리

절도 시험에서 다음 네 결과를 각각 구성할 수 있어야 한다.

```text
성공 + 미발각
성공 + 발각
실패 + 흔적
실패 + 미발각
```

합격 기준은 다음과 같다.

- 목적 달성과 노출이 하나의 성공값으로 묶이지 않음
- 발각되지 않은 절도로 즉시 마을 전체 평판이 변하지 않음

#### C08 — 정보 전파 경계

한 명만 절도를 직접 목격하고 일부 주민에게만 전달한다.

합격 기준은 다음과 같다.

- 목격자는 직접 목격 기억을 가짐
- 전달받은 사람은 전언으로 기록함
- 듣지 못한 사람은 아무 반응도 하지 않음
- 소문을 들었지만 믿지 않은 사람은 평판을 바꾸지 않음

#### C09 — 성향 변화 속도

규범적인 인물이 한 번 절도한 경우와 반복한 경우를 비교한다.

합격 기준은 다음과 같다.

- 한 번의 행동으로 성향이 급변하지 않음
- 의미 있는 충돌은 변화 압력으로 기록됨
- 주간 최대 `±2`를 넘지 않음
- 동일한 저위험 반복 행동의 효과가 감소함
- 실제 경험이 이후 선택 점수에 반영됨

#### C10 — 배경 인물의 중심인물화

최초 핵심 인물이 아닌 주민의 가구를 위험 상태로 만든다.

합격 기준은 다음과 같다.

- 해당 주민이 상세 판단 대상으로 활성화됨
- 핵심 인물과 같은 행동, 기억 및 정보 규칙을 사용함
- 전용 각본 없이 사건의 행위자가 될 수 있음

#### 60일 통합 시험

기준 인물 구성 A와 시드 1001로 60일을 실행한다. 이때 플레이어도 NPC 규칙으로 자동 판단한다.

다음 결과는 강제하지 않는다.

```text
절도 발생 = 필수 아님
촌장 축출 = 필수 아님
사망자 발생 = 필수 아님
마을 생존 = 필수 아님
특정 인물의 승리 = 필수 아님
```

대신 다음을 요구한다.

- 최소 한 명의 행동 우선순위가 경험 때문에 변경됨
- 최소 한 명의 배경 인물이 상세 판단 대상으로 올라옴
- 발생한 모든 상세 행동에 추적 가능한 이유가 있음
- 관찰되지 않은 사건이 전지적으로 전파되지 않음
- 식량, 건강 및 관계 변화가 사건 기록과 일치함
- 반응 연쇄와 기억량이 제한 범위 안에 있음
- 같은 실행을 반복하면 동일한 60일 결과가 나옴

#### 통합 반대 조건

기준 실행에서 한 조건만 바꾼다.

| 변형 | 변경 사항 | 관찰 가설 |
|---|---|---|
| V1 충분한 구호 | 공동창고 식량 증가 | 굶주림·절도 압력 감소 |
| V2 조기 실사 | 부족분이 일찍 공개됨 | 횡령 추정 대신 확인 정보 증가 |
| V3 알려진 강한 경비 | 주민들이 경비 강화를 앎 | 창고 절도 후보와 선택 감소 |
| V4 숨겨진 강한 경비 | 실제 경비만 강화 | 선택은 비슷하나 실패·발각 증가 |
| V5 외부 교역 가능 | 신뢰할 만한 상인 정보 제공 | 거래·차용 행동 증가 |
| V6 정보 차단 | 특정 주민이 창고 정보를 모름 | 해당 창고 관련 행동 후보 제거 |

표의 방향은 결과 판정용 정답이 아니라 비교 실행 전에 적는 관찰 가설이다. 반대 방향, 무변화 또는 예상하지 못한 선택도 기계 규칙 위반이 없다면 유효한 관찰 결과다. 모델이 둔감하거나 이상해 보이면 그 사실을 기록하고, 가중치·초기 상태·정의를 바꾸려면 별도의 설계 변경 승인을 받는다.

#### 최종 판정

```text
PASS
- I01~I10 전부 통과
- 60일 실행에서 치명적 불변조건 위반 없음
- C01~C10의 입력·후보·계산·선택·결과 기록 완료
- 발생한 판단과 정보 전파의 계산 경로를 감사할 수 있음

OBSERVED
- 기계 규칙은 통과했으나 행동 변화가 거의 없거나 특정 행동만 반복
- 예상과 다른 방향 또는 이상해 보이는 행동이 발생
- gameplay utility와 인간적 개연성은 아직 성립하지 않았다고 기록
- 변경이 필요하면 별도의 설계 변경안과 승인 후 재검증

FAIL
- 비결정적 재실행
- 전지적 NPC 반응
- 자원 복제 또는 음수 자원
- 동결된 계산 정의와 실제 결과가 불일치
- 판단 기록으로 계산 경로를 감사할 수 없음
```

`OBSERVED` 결과는 자동 실패도 자동 튜닝 근거도 아니다. 확대 여부와 모델 변경은 별도 설계 결정으로 다룬다. `FAIL` 상태에서는 NPC 수, 사건 종류, 그래픽 및 세계 규모를 확대하지 않는다.

이 검증안은 원하는 줄거리나 특정 변화 방향이 나왔다는 이유로 성공을 선언하지 않는다. 동결된 시스템을 실행하고 생성된 인과 기록을 관찰하며, 합격 여부는 기계 규칙으로만 판정한다.

## 20. 승인된 잠정 설계 17

### 결정 17. 구현 단계와 중단 기준

전체 게임을 한꺼번에 만들지 않는다. 각 구현 단계는 독립적으로 검증할 수 있어야 하며, 합격 기준을 통과해야 다음 단계로 넘어간다.

#### 기본 개발 원칙

```text
한 단계 = 하나의 명확한 기능 범위
한 단계 = 독립 검증 가능
검증 실패 = 다음 단계 진행 금지
main 브랜치 = 항상 실행 가능한 상태
대규모 선행 데이터 작성 = 금지
UI보다 인과 엔진 우선
```

각 단계는 별도 브랜치와 PR로 진행하고 테스트 통과 후에만 `main`에 병합한다.

#### 권장 저장소 구조

```text
project.godot

src/
  simulation/
    model/
    time/
    decision/
    resolution/
    events/
    knowledge/
  application/

data/
  definitions/
  reference_cast/

ui/

tests/
  unit/
  scenarios/
  fixtures/

docs/
```

시뮬레이션 계층은 UI와 `SceneTree` 없이도 실행할 수 있어야 한다. 화면을 닫아도 같은 입력과 시드에서 같은 결과가 나와야 한다.

#### M0 — Godot 기반 구축

구현 내용은 다음으로 제한한다.

- Godot 4.7.2 프로젝트 생성
- GDScript 정적 타입 정책 적용
- Windows에서 프로젝트 실행 확인
- 화면 없이 실행 가능한 테스트 진입점
- 최소 폴더 구조와 README 실행법
- 빈 테스트 한 개를 실행하고 종료 코드 반환

합격 기준은 다음과 같다.

```text
Godot 편집기 실행 = 성공
Windows 실행 = 성공
Headless smoke test = exit 0
정적 타입 오류 = 0
게임 시스템 구현 = 없음
```

## 21. 승인된 잠정 설계 18

### 결정 18. M1 상태 모델과 직렬화 계약

M1은 인물이 판단하거나 시간이 흐르는 단계가 아니다. 세 명의 인물과 그들의 가구, 방향성 관계, 사건, 정보 및 기억을 모호하지 않게 표현하고, 저장 순서와 운영체제에 관계없이 동일하게 복원·식별할 수 있는지를 검증한다.

M1이 통과해도 인간다운 판단, 인과 모델의 유용성 또는 게임의 재미를 주장하지 않는다.

#### 기본 기술 선택

```text
MODEL OBJECT = STATICALLY TYPED GDSCRIPT RefCounted
REFERENCE = OBJECT POINTER가 아닌 STRING ID
SAVE FORMAT = HUMAN-READABLE JSON
SIMULATION NUMBER = BOUNDED INTEGER ONLY
64-BIT SEED / RNG STATE = HEX STRING
CANONICAL HASH = SHA-256
TEST CAST = 3 PERSONS
```

모델은 `Node`, `SceneTree` 및 UI에 의존하지 않는다. 모델 사이에는 직접 객체 참조를 연결하지 않고 ID만 저장한다. 이 규칙은 순환 참조, 숨은 소유권 및 직렬화 순서 의존성을 방지한다.

공식 API 기준은 다음과 같다.

- [Godot 4.7 RefCounted](https://docs.godotengine.org/en/4.7/classes/class_refcounted.html)
- [Godot 4.7 JSON](https://docs.godotengine.org/en/4.7/classes/class_json.html)
- [Godot 4.7 HashingContext](https://docs.godotengine.org/en/4.7/classes/class_hashingcontext.html)

#### 모델별 책임

| 모델 | M1에서 표현하는 최소 상태 |
|---|---|
| `WorldState` | 스키마 버전, 시나리오 ID, 날짜, RNG 상태, ID counter, ruleset 식별자, 플레이어 인물 ID 및 상태 collection |
| `PersonState` | 신원, 가구·직업·역할 ID, 생존·건강, 성향, 가치관, 감정, 욕구, 목표 및 관련 상태 ID |
| `HouseholdState` | 구성원 ID, 식량, 재산, 하루 필요량, 생업, 부양 부담 및 거주 상태 |
| `RelationState` | 방향성 있는 신뢰, 애정, 두려움, 원한 및 의무감 |
| `EventRecord` | 실제 사건, 발생일, 행위자, 대상, 행동, 결과, 장소, 목격자 및 공개 여부 |
| `InformationState` | 주장, 보유자, 목격·전언 구분, 최초 정보원, 전달자, 신뢰도, 비밀 여부 및 습득일 |
| `MemoryState` | 소유자, 연결 사건·정보, 인식한 행동·결과, 관련 인물, 감정, 중요도, 발생일 및 기억 단계 |
| `ActionDefinition` | 행동 정의 ID, 버전 및 M1에서 검증 가능한 정적 의미 정보 |
| `DecisionRecord` | 후보, 불가 사유, 평가 근거, 의도, 선택, 결과 및 변화 압력에 대한 감사 기록 |

`DecisionRecord`는 감사용 불변 기록이며 simulation이 미래 판단을 위해 다시 읽지 않는다. 미래의 성향 변화에 필요한 누적 압력은 M5에서 명시적인 mutable state로 도입한다. 로그가 숨은 게임 상태가 되어서는 안 된다.

`ActionDefinition`은 mutable `WorldState`에 복제하지 않는다. 세계 상태에는 사용한 `ruleset_id`와 `ruleset_hash`만 포함하여 규칙 변경 여부를 식별한다.

#### ID와 참조

무작위 UUID를 사용하지 않는다. 모든 동적 ID는 종류별 단조 증가 counter로 생성하며, counter 자체를 `WorldState`에 저장한다.

```text
person:000001
household:000001
event:000001
information:000001
memory:000001
decision:000001
```

방향성 관계 ID는 양 끝의 인물 ID를 명시한다.

```text
relation:person:000001->person:000003
relation:person:000003->person:000001
```

두 관계는 서로 다른 상태다. 모든 참조는 유효한 ID를 가리켜야 하며, 중복 ID와 끊어진 참조는 불러오기 단계에서 거부한다.

플레이어 전용 상태 클래스는 만들지 않는다. `WorldState.player_person_id`가 일반 `PersonState` 하나를 가리킨다.

#### 직렬화 표현

각 모델은 명시적인 primitive data로 변환한다. 저장 payload에는 다음 형식만 허용한다.

```text
String
bounded int
bool
null
Array
Dictionary with String keys
```

Godot JSON은 JSON number에서 정수와 실수 타입을 구분하지 않으므로 다음 규칙을 적용한다.

- 성향, 감정, 관계, 자원 및 날짜는 안전 범위의 정수만 사용함
- JSON parse 후 각 필드를 명시적인 정적 타입으로 검증·복원함
- ID는 항상 문자열로 저장함
- 64비트 seed와 RNG state는 16진수 문자열로 저장함
- simulation state에서 임의 float, `NaN` 및 무한대를 금지함
- writer는 strict JSON만 생성하며 reader는 schema와 모든 필드 타입을 다시 검증함

저장 envelope의 최소 구조는 다음과 같다.

```text
schema_version
ruleset_id
ruleset_hash
state
audit
state_hash
```

`state`에는 미래 결과에 영향을 줄 수 있는 mutable state가 들어간다. `audit`에는 simulation이 읽지 않는 `DecisionRecord`가 들어간다. 저장 시각, 파일 경로 및 UI 상태는 payload의 의미 상태에 포함하지 않는다.

M1에서는 schema migration을 구현하지 않는다. 알 수 없는 `schema_version`은 명시적으로 실패한다.

#### 표준 상태와 상태 해시

표준화 절차는 다음 순서를 고정한다.

```text
WorldState
→ primitive data 변환
→ Dictionary key 사전순 정렬
→ 모든 entity collection ID순 정렬
→ 참조 ID collection 정렬
→ 공백 없는 canonical JSON
→ UTF-8 bytes
→ SHA-256
```

Dictionary key 정렬만으로는 충분하지 않다. JSON array는 원래 순서를 유지하므로, 의미상 순서가 없는 모든 collection을 명시적으로 ID순 정렬한 뒤 직렬화한다.

상태 해시에는 미래 simulation 결과에 영향을 줄 수 있는 다음 요소를 포함한다.

```text
INCLUDE
- schema와 ruleset 식별자
- 날짜와 RNG 상태
- 종류별 ID counter
- player_person_id
- 인물, 가구 및 방향성 관계
- 객관적 사건, 정보 및 기억
```

다음은 상태 해시에서 제외한다.

```text
EXCLUDE
- 저장 시각과 파일 경로
- JSON 들여쓰기와 key 입력 순서
- UI 및 editor 상태
- simulation이 읽지 않는 DecisionRecord 감사 로그
```

어떤 데이터가 미래 결과에 영향을 주기 시작하면 반드시 mutable state로 승격하고 상태 해시에 포함한 뒤에만 사용할 수 있다.

#### 세 명의 기준 fixture

M1 기준 상태는 다음 세 명으로 제한한다.

```text
person:000001 = 플레이어 / 공동창고 하급 관리 보조
person:000002 = 배우자 / 같은 가구
person:000003 = 촌장 / 별도 가구
```

fixture에는 최소한 다음을 둔다.

- 두 개의 가구
- 플레이어에서 촌장으로 향하는 관계와 촌장에서 플레이어로 향하는 서로 다른 관계
- 객관적 사건 하나
- 플레이어만 보유한 정보 하나
- 플레이어가 가진 기억 하나
- 감사용 판단 기록 하나
- `player_person_id = person:000001`

M1에서는 이 인물들이 판단하거나 행동하지 않는다. fixture는 상태 표현과 직렬화 검증만을 위한 것이다.

#### M1 필수 시험

| ID | 시험 | 합격 기준 |
|---|---|---|
| M1-T01 | 저장 후 복원 | 의미 상태와 감사 기록 완전 동일 |
| M1-T02 | collection 순서 변경 | canonical state hash 동일 |
| M1-T03 | 의미 있는 값 하나 변경 | canonical state hash 변경 |

| M1-T05 | 존재하지 않는 ID 참조 | validation 실패 |

| M1-T07 | 플레이어 구조 확인 | 일반 `PersonState`를 사용하고 별도 `PlayerState`가 없음 |

추가로 JSON writer가 생성한 canonical payload와 frozen fixture SHA-256을 저장소에 보존한다. 해시가 바뀌면 스키마 변경인지 결함인지 명시적으로 판정해야 하며 기대값을 조용히 갱신하지 않는다.

M1에서는 각 상태의 구조와 불변조건만 구현한다. 상태 변화 규칙은 해당 마일스톤이 승인되기 전까지 추가하지 않는다.

#### M1 합격 주장 경계

M1 통과가 증명하는 것은 다음뿐이다.

> 세 명의 인물과 그들의 관계·사건·정보·기억을 모호하지 않은 상태로 표현하고, 저장 순서와 운영체제에 관계없이 동일하게 복원·식별할 수 있다.

M1 통과는 NPC 판단의 개연성, 인과 모델의 외부 타당성, 장기 simulation 안정성 또는 게임의 재미를 증명하지 않는다.

결정 18의 계약에 따라 M1 구현이 승인되었고, 세 명의 기준 fixture와 M1-T01~T10을 구현했다. 로컬·Linux·Windows에서 동일한 frozen fixture SHA-256과 전체 시험 통과를 확인하여 `M1 PASS`로 확정한다. M2 시간·자원 시스템의 구현 권한은 부여되지 않았다.

## 22. 승인된 잠정 설계 19

### 결정 19. M2 하루 진행과 자원 보존 계약

M2는 NPC가 판단하는 단계가 아니다. 하루가 고정된 순서로 진행될 때 식량이 설명 없이 생성·소멸하지 않고, 부족한 식량이 주민의 굶주림과 건강에 결정론적으로 반영되는지를 검증한다.

M2의 중심 질문은 다음과 같다.

> 시간이 하루씩 흐를 때 식량이 설명 없이 생성·소멸하지 않고, 부족한 식량이 주민의 굶주림과 건강 상태에 재현 가능하게 반영되는가?

M2가 통과해도 배급 정책의 인간적 타당성, NPC의 자율성, 가뭄 모델의 현실성 또는 게임의 재미를 주장하지 않는다.

#### 기준 규모

M2 기준 fixture는 다음으로 제한한다.

```text
HOUSEHOLDS = 3
PERSONS = 8
VILLAGE STOREHOUSE = 1
BASELINE RUN = 10 DAYS
AUTONOMOUS DECISIONS = NONE
```

플레이어도 일반 주민과 동일한 시간·소비·건강 규칙을 적용받는다. M2에서는 어떤 인물도 식량을 요청하거나, 훔치거나, 양보하거나, 배급 정책을 선택하지 않는다.

#### 추가 상태

M2는 최소한 다음 상태를 표현한다.

- 인물별 하루 식량 필요량
- 가구별 사유 식량 저장소
- 마을 공동창고 식량 저장소
- 인물별 굶주림과 건강
- 현재 날짜와 하루 처리 단계
- 식량 이동·소비 기록

가구와 공동창고의 식량을 서로 다른 임시 필드나 예외 코드로 처리하지 않는다. 동일한 `ResourceStoreState` 규칙으로 표현한다.

```text
resource_store:village_granary
resource_store:household:000001
resource_store:household:000002
resource_store:household:000003
```

`ResourceStoreState`에는 저장소 ID, 소유 범주, 소유자 참조, 자원 종류 및 현재 정수 수량을 둔다. M2의 자원 종류는 `food` 하나뿐이다.

모든 식량 변화는 `ResourceTransactionRecord`로 설명할 수 있어야 한다. 기록에는 최소한 거래 ID, 날짜, 원천 저장소, 목적 저장소 또는 소비 sink, 수량 및 사유를 둔다. 기록을 남기지 않은 직접 수치 변경은 금지한다.

M2 구현으로 기존 직렬화 schema를 변경해야 한다면 변경 이유, 새 버전, 기존 M1 fixture 처리 및 frozen hash 영향을 PR에서 명시한다. M1 frozen fixture와 기대 해시를 조용히 갱신하지 않는다.

#### 하루 처리 순서

하루 처리 순서는 다음으로 고정한다.

```text
DAY_START
→ 식량 필요량 확정
→ 가구별 배분량 계산
→ 실제 식량 소비
→ 부족량 계산
→ 굶주림 갱신
→ 건강 갱신
→ 자원 보존 검증
→ DAY_END
```

- 한 인물의 하루 필요량은 `DAY_START`에 한 번만 확정함
- 실제 저장소 잔량을 초과한 소비를 금지함
- 한 인물이 같은 날 두 번 소비되는 것을 금지함
- 날짜는 전체 단계가 성공한 뒤에만 정확히 1 증가함
- 중간 단계 실패 시 완료된 하루로 기록하지 않음
- M2에서는 처리 도중 저장·재개를 구현하지 않음

하루 처리 단계 자체는 미래 결과에 영향을 줄 수 있는 상태다. 저장 가능한 경계는 완전한 `DAY_END` 상태로 제한하고, 중간 단계에서 발견된 상태는 validation 실패로 처리한다.

#### 식량 부족 시 기계적 배분

M2에는 가족 내 우선순위, 희생, 권력 또는 협상 판단을 넣지 않는다. 가구 식량이 부족하면 생존 구성원에게 필요량 대비 같은 비율로 배분한다.

정수 단위 배분 후 남는 식량은 다음 규칙으로 처리한다.

```text
1. 생존 구성원을 canonical person ID순으로 정렬
2. day_index를 시작 offset으로 사용
3. 필요량이 남은 사람에게 한 단위씩 순환 배분
4. 저장소 잔량 또는 전체 필요량이 0이 되면 종료
```

같은 상태와 같은 날짜에서는 항상 같은 결과가 나와야 한다. `day_index` offset은 낮은 ID가 매일 영구적으로 먼저 배정받는 편향을 줄이기 위한 기계적 규칙이며, 인물의 선택이나 사회적 배급 정책으로 해석하지 않는다.

#### 자원 보존식

매일 다음 식을 반드시 만족해야 한다.

```text
시작 식량
= 종료 식량
+ 실제 소비량
+ 명시적 손실량
```

M2에는 생산, 수확, 부패, 도난 및 파괴가 없으므로 `명시적 손실량 = 0`이다. 따라서 M2의 실제 보존식은 다음과 같다.

```text
시작 식량 = 종료 식량 + 실제 소비량
```

가구별, 공동창고별 및 전체 fixture 수준에서 각각 보존식을 검증한다. 음수 수량, 원천 없는 유입, 목적 없는 유출, 0 이하 거래 및 동일 거래 ID의 중복 적용을 거부한다.

`ResourceTransactionRecord`는 이미 완료된 변화의 감사 근거다. 미래 simulation이 거래 기록 자체를 읽어 다음 결과를 바꾸지 않는다. 미래 판단에 필요한 누적 상태가 생기면 별도의 mutable state로 승격하고 상태 해시에 포함해야 한다.

#### 굶주림과 건강의 최소 규칙

M2에서는 현실적인 영양·질병 모델을 만들지 않는다. 굶주림과 건강은 `0~100` 범위의 정수로 제한한다.

- 필요량 전부 섭취: 굶주림 감소
- 필요량 일부 섭취: 부족 비율에 따라 굶주림 증가
- 전혀 섭취하지 못함: 더 큰 굶주림 증가
- 굶주림이 건강 손상 임계값 미만: 건강 변화 없음
- 임계값 이상인 상태가 이어짐: 건강 감소
- 건강과 굶주림은 항상 `0~100`으로 제한

정확한 증가량, 감소량 및 임계값은 M2 fixture용 잠정 상수로 구현 PR에서 명시한다. 테스트 결과를 원하는 방향으로 만들기 위해 실행 후 조용히 조정하지 않는다.

#### M2 필수 시험

| ID | 시험 | 합격 기준 |
|---|---|---|
| M2-T01 | 하루 진행 | 전체 단계 성공 후 날짜가 정확히 1 증가 |
| M2-T02 | 충분한 식량 | 생존자 전원이 필요량을 충족하고 보존식 성립 |
| M2-T03 | 부족한 식량 | 음수 식량 없이 동일 비율·고정 순환 규칙으로 배분 |
| M2-T04 | 자원 보존 | 시작량과 종료량·실제 소비량이 완전 일치 |
| M2-T05 | 중복 소비 | 한 인물의 동일 날짜 소비가 최대 1회 |
| M2-T06 | 굶주림 변화 | 실제 섭취 부족의 방향과 크기에 일관되게 반응 |

| M2-T10 | 처리 순서 위반 | 중복·누락·역순 단계가 명시적으로 실패 |


#### M2 합격 주장 경계

M2 통과가 증명하는 것은 다음뿐이다.

> 세 가구·여덟 명과 공동창고의 식량 상태가 고정된 하루 처리 순서에 따라 보존되고, 실제 섭취 부족이 굶주림과 건강에 결정론적으로 반영되며, 완전한 날 단위 저장 후에도 같은 결과를 재현할 수 있다.

M2 통과는 가뭄의 현실성, 배급의 정당성, 인물의 판단, 사회적 인과 또는 재미를 증명하지 않는다.

결정 19의 승인은 M2 계약만 확정한다. M2 구현 권한은 별도의 `M2 구현 승인` 전까지 부여되지 않는다.

## 23. 승인된 잠정 설계 20

### 결정 20. M2 세부 구현 명세

결정 20은 결정 19의 M2 계약을 실제 코드 작업 단위, schema, 상수, fixture 및 시험 순서로 고정한다. 이 명세는 구현 중 임의 해석과 수치 조정을 막기 위한 사전 계약이다.

#### Schema 전략

M2는 기존 schema 1에 선택 필드를 덧붙이지 않는다. schema 1과 schema 2를 명시적으로 분리한다.

```text
SCHEMA 1
= M1 상태 모델
= 기존 frozen fixture와 SHA-256 보존

SCHEMA 2
= M2 시간·자원 상태
= ResourceStoreState와 하루 진행 상태 추가
```

구현 규칙은 다음과 같다.

- schema 1과 schema 2를 각각 읽고 쓸 수 있음
- schema 1을 schema 2로 자동 변환하지 않음
- schema별 validation과 primitive data 변환을 분리함
- 기존 M1 fixture와 SHA-256을 변경하지 않음
- M2 전용 fixture와 SHA-256을 별도로 생성함
- 알 수 없는 schema는 명시적으로 거부함
- 새 `WorldState`의 기본 schema는 2로 변경함
- M1 fixture factory는 schema 1을 명시함

이는 schema migration 구현이 아니다. 두 frozen schema를 각각 독립적으로 지원하는 방식이다.

#### PersonState 확장

schema 2의 `PersonState`에 다음을 추가한다.

```text
daily_food_need_units: int
severe_hunger_days: int
```

굶주림은 기존 `need_scores["hunger"]`를 유일한 원본으로 사용한다. 별도의 `hunger` 필드를 추가하지 않는다.

```text
health = 1~100
need_scores["hunger"] = 0~100
daily_food_need_units = 0~10
severe_hunger_days = 0~365
```

M2는 사망을 구현하지 않는다. 건강 갱신 결과가 0 이하가 될 상황에서는 1로 조용히 고정하거나 `alive`를 변경하지 않고, `M2_DEATH_NOT_IMPLEMENTED` 오류로 그날 진행 전체를 실패시킨다.

#### HouseholdState 확장과 legacy 필드

schema 2의 `HouseholdState`에 다음을 추가한다.

```text
resource_store_id: String
```

기존 필드 중 다음은 schema 1 전용 legacy 필드로 남긴다.

```text
food_units
daily_food_need_units
```

schema 2에서는 두 legacy 필드를 직렬화, validation 및 계산에 사용하지 않는다. 가구의 하루 필요량은 생존 구성원의 `daily_food_need_units` 합계로 계산한다. schema 2 식량의 유일한 원본은 `ResourceStoreState.quantity`다.

#### ResourceStoreState

`ResourceStoreState`는 다음 필드를 가진 `RefCounted` 데이터 객체다.

```text
id: String
owner_kind: String
owner_id: String
resource_type_id: String
quantity: int
```

M2 허용 범위는 다음과 같다.

```text
owner_kind = village | household
resource_type_id = food
quantity = 0~2,147,483,647
```

저장소 ID는 결정 19의 형식을 그대로 사용한다.

```text
resource_store:village_granary
resource_store:household:000001
resource_store:household:000002
resource_store:household:000003
```

`owner_kind = household`이면 `owner_id`는 존재하는 `HouseholdState`를 가리켜야 한다. `owner_kind = village`이면 M2에서는 `owner_id = village:main`만 허용한다.

#### ResourceTransactionRecord

`ResourceTransactionRecord`는 다음 필드를 가진 감사 기록이다.

```text
id: String
day_index: int
sequence_index: int
resource_type_id: String
source_store_id: String
destination_store_id: String
consumer_person_id: String
quantity: int
reason_id: String
```

두 가지 형태만 허용한다.

```text
TRANSFER
destination_store_id = 존재
consumer_person_id = 빈 문자열

CONSUMPTION
destination_store_id = 빈 문자열
consumer_person_id = 존재
```

다음 거래는 validation 단계에서 거부한다.

- 수량이 0 이하임
- source와 destination이 동일함
- 존재하지 않는 저장소나 인물을 참조함
- source 잔량을 초과함
- 같은 거래 ID를 중복 적용함
- 같은 인물이 같은 날짜에 두 번 소비함
- destination과 consumer가 동시에 존재함
- destination과 consumer가 모두 존재하지 않음

거래 ID는 기존 종류별 counter 규칙을 사용한다.

```text
resource_transaction:000001
```

#### Schema 2 저장 envelope

Schema 1 envelope는 M1 frozen 형식을 그대로 유지한다. Schema 2는 다음 필드를 사용한다.

```text
schema_version
ruleset_id
ruleset_hash
state
audit
resource_audit
state_hash
```

`resource_audit`에는 `ResourceTransactionRecord` 배열을 둔다. 이 기록은 미래 simulation의 입력이 아니므로 상태 해시에서 제외한다.

Schema 2 상태 해시에 포함하는 M2 요소는 다음과 같다.

```text
day_index
day_phase
인물별 daily_food_need_units
need_scores["hunger"]
health
severe_hunger_days
가구별 resource_store_id
ResourceStoreState 전체
M2 ruleset 식별자와 hash
기존 M1 mutable state
```

다음은 상태 해시에서 제외한다.

```text
DecisionRecord
ResourceTransactionRecord
저장 시각과 경로
UI와 editor 상태
개발 로그
```

#### M2 ruleset 상수

M2 수치를 처리 코드에 직접 흩어 쓰지 않는다. 다음 파일의 정적 타입 상수로 모은다.

```text
src/simulation/time/m2_resource_rules.gd
```

승인된 잠정 상수는 다음과 같다.

```text
FULL_MEAL_HUNGER_RECOVERY = 6
SHORTFALL_HUNGER_SCALE = 24
SEVERE_HUNGER_THRESHOLD = 80
HEALTH_DAMAGE_DELAY_DAYS = 2
DAILY_HEALTH_DAMAGE = 5
```

상수 묶음을 primitive data로 변환하여 `ruleset_hash`에 포함한다.

```text
ruleset_id = drought-prototype-rules-v2
```

상수를 변경하면 schema 2 상태 해시와 frozen fixture 결과도 달라져야 한다. 변경 이유와 전후 시험을 별도 PR에 기록하지 않은 수치 변경은 금지한다.

#### 굶주림 계산

각 인물의 하루 필요량, 섭취량 및 부족량을 다음으로 정의한다.

```text
N = daily_food_need_units
E = 실제 섭취량
S = max(0, N - E)
```

필요량을 모두 섭취했다면 다음을 적용한다.

```text
H_next = max(0, H - 6)
```

부족하다면 다음을 적용한다.

```text
delta_hunger = ceil(24 × S / N)
H_next = min(100, H + delta_hunger)
```

실수 계산은 사용하지 않는다. 올림은 다음 정수식으로 구현한다.

```text
delta_hunger = (24 × S + N - 1) / N
```

예시는 다음과 같다.

| 필요량 | 섭취량 | 굶주림 변화 |
|---:|---:|---:|
| 2 | 2 | -6 |
| 2 | 1 | +12 |
| 2 | 0 | +24 |
| 1 | 0 | +24 |

`N = 0`인 인물은 식량 거래와 굶주림·건강 갱신 대상에서 제외한다.

#### 건강 계산

건강은 굶주림 갱신 후 계산한다.

```text
새 굶주림 >= 80
→ severe_hunger_days += 1

새 굶주림 < 80
→ severe_hunger_days = 0
```

건강 변화는 다음과 같다.

```text
severe_hunger_days < 2
→ 건강 변화 없음

severe_hunger_days >= 2
→ health -= 5
```

건강 감소는 두 번째 연속 심각 굶주림 날부터 매일 적용한다. M2에는 질병, 자연회복, 부상, 연령별 건강 차이 및 사망을 넣지 않는다.

#### 부족 식량 배분 알고리즘

각 가구에서 생존 구성원을 canonical person ID순으로 정렬한다.

```text
A = 가구 저장소의 사용 가능한 식량
T = 전체 필요량
N_i = 인물 i의 필요량
```

`A >= T`이면 각 인물에게 필요량을 그대로 배정한다. `A < T`이면 1차 배분을 다음으로 계산한다.

```text
B_i = floor(A × N_i / T)
```

남은 수량은 다음과 같다.

```text
R = A - sum(B_i)
```

나머지 배분 규칙은 다음과 같다.

```text
시작 위치 = 현재 world.day_index % 생존 구성원 수
canonical person ID순 목록을 순환
아직 필요량이 남은 인물에게 1단위씩 배정
R = 0이면 종료
```

이 알고리즘은 필요량 비례, 정수 계산, 결정론 및 낮은 ID의 영구 우선권 완화를 목적으로 한다. 인물의 도덕적 선택이나 사회적 배급 정책으로 해석하지 않는다.

#### 원자적 하루 진행

`DayProcessor`는 입력 `WorldState`를 직접 수정하지 않는다.

```text
advance_day(current_world: WorldState) -> DayAdvanceResult
```

`DayAdvanceResult`는 다음을 가진다.

```text
ok: bool
errors: Array[String]
next_world: WorldState
resource_transactions: Array[ResourceTransactionRecord]
before_total: int
after_total: int
consumed_total: int
```

처리 순서는 다음으로 고정한다.

1. 입력 세계 validation
2. primitive data를 통한 입력 세계 복제
3. 복제본을 대상으로 하루 계획 작성
4. 계획 validation
5. 거래 적용
6. 굶주림 갱신
7. 건강 갱신
8. 저장소별·전체 자원 보존 검증
9. 날짜 1 증가
10. 최종 state hash 생성
11. 성공한 복제본 반환

어느 단계에서든 실패하면 다음을 보장한다.

```text
입력 current_world 변경 = 0
day_index 증가 = 0
부분 거래 기록 반환 = 0
next_world = null
```

#### 단계 순서 보호

내부 `DayPhaseGuard`는 다음 상태 전이만 허용한다.

```text
DAY_END
→ NEEDS_FIXED
→ ALLOCATION_PLANNED
→ CONSUMPTION_APPLIED
→ HUNGER_UPDATED
→ HEALTH_UPDATED
→ CONSERVATION_VERIFIED
→ DAY_END
```

단계를 생략, 중복 또는 역순 호출하면 즉시 실패한다. 저장 가능한 `WorldState.day_phase`는 `DAY_END`뿐이다. 중간 단계 상태는 serialization validation을 통과하지 못한다.

#### M2 기준 fixture

M2 fixture는 세 가구, 여덟 명 및 공동창고 하나로 고정한다. 모든 인물은 초기 `health = 100`, `hunger = 0`, `severe_hunger_days = 0`이다.

##### 가구 1 — 플레이어 가족

```text
person:000001 = 플레이어 / 필요량 2
person:000002 = 배우자 / 필요량 2
person:000004 = 자녀 / 필요량 1

총 필요량 = 5
초기 식량 = 22
```

4일간 전원 필요량을 충족하고 5일째 부분 배분이 발생한다.

##### 가구 2 — 촌장 가족

```text
person:000003 = 촌장 / 필요량 2
person:000005 = 촌장 배우자 / 필요량 2
person:000006 = 노인 부양가족 / 필요량 1

총 필요량 = 5
초기 식량 = 46
```

9일간 전원 필요량을 충족하고 10일째 부분 배분이 발생한다.

##### 가구 3 — 노동자 형제

```text
person:000007 = 노동자 / 필요량 2
person:000008 = 노동자 / 필요량 2

총 필요량 = 4
초기 식량 = 13
```

3일간 전원 필요량을 충족하고 4일째 부분 배분이 발생한다.

##### 공동창고

```text
초기 식량 = 100
자동 배급 = 없음
```

공동창고는 M2의 10일 실행에서 자동으로 가구를 돕지 않는다. 촌장의 배급 판단을 M2에 몰래 구현하지 않기 위한 경계다.

초기 총식량과 10일 뒤 기대값은 다음과 같다.

```text
초기 총식량 = 22 + 46 + 13 + 100 = 181
10일 뒤 가구 저장소 합계 = 0
10일 뒤 공동창고 = 100
10일간 실제 소비 = 81
```

따라서 다음 보존식이 성립해야 한다.

```text
181 = 100 + 81
```

M2 fixture의 day-10 canonical JSON과 SHA-256은 구현 후 최초 green 결과에서 동결한다. 원하는 hash를 사전에 정하거나 실패 후 조정하지 않는다.

#### 구현 순서와 단계별 중단 조건

##### M2-A — schema와 모델

- schema 1 frozen 직렬화와 hash 보존
- schema 2 모델과 validation 추가
- ResourceStore와 거래 기록 직렬화

중단 조건:

```text

```

##### M2-B — 자원 처리

- 저장소 간 명시적 transfer
- 저장소에서 인물로 consumption
- 잔량·참조·중복 검증
- 저장소별·전체 보존식

중단 조건:

```text
→ 즉시 중단
```

- 굶주림 갱신
- 건강 갱신
- 단계 guard
- 원자적 `next_world` 반환

- 3가구·8명 fixture
- 날짜별 state hash
- 10일 연속 실행

```text
M2 PASS
= 하루 진행·식량 보존·굶주림·건강의
  최소 기계 규칙이 결정론적으로 작동함

M2 PASS
≠ NPC 판단이 작동함
≠ 가뭄이 구현됨
≠ 게임의 재미가 검증됨
```

결정 20의 승인만으로는 M2 코드 작성 권한이 부여되지 않았다. 이후 별도의 `M2 구현 승인`이 2026-09-01에 부여되었고, 구현은 M2-T01~T12와 M2-R01~R08 및 Linux·Windows CI를 통과한 최초 green 결과로 동결했다.

## 24. 승인된 잠정 설계 21

### 결정 21. M3 최초 판단 엔진 계약

M3는 처음으로 인물이 실행 가능한 행동 후보를 만들고 비교하여 하나를 선택하는 순수 판단 계층을 추가한다. 행동의 실제 성공·실패, 상대방의 응답, 자원 이전과 세계 변화는 처리하지 않는다.

#### 핵심 원칙 — 정답 없는 관찰

> M3는 특정 행동, 효용 방향 또는 이야기 결과를 합격 조건으로 삼지 않는다. 동결된 입력과 규칙으로 생성된 후보·구성요소·선택을 관찰한다. 합격 여부는 계산 정확성, 재현성, 정보 경계, 상태 불변성과 감사 가능성으로만 판정한다. 예상한 방향과 다른 결과는 규칙 위반이 없는 한 실패가 아니라 관찰 결과다.

M3에서 다음 두 층을 분리한다.

| 층 | 판정 대상 | 결과 |
|---|---|---|
| 기계 검증 | 후보 자격, 계산식, 결정론, 정보 경계, 입력 불변성, 감사 기록, 운영체제 일치 | `PASS` 또는 `FAIL` |
| 행동 관찰 | 어떤 행동이 선택됐는지, 반대 조건에서 각 구성요소와 선택이 어떻게 달라졌는지 | `OBSERVED` |

다음과 같은 기록은 서로 모순되지 않는다.

```text
M3 MECHANICS = PASS
OBSERVED MODEL BEHAVIOR = INERT
GAMEPLAY UTILITY = NOT ESTABLISHED
```

행동이 지나치게 둔감하거나 이상해 보이더라도 기계 규칙을 지켰다면 같은 계약 안에서 수치나 fixture를 몰래 조정하지 않는다. 코드가 동결 정의와 다르게 계산했거나 정의 자체에 모순이 있을 때만 같은 계약 안에서 수정할 수 있다. 모델의 성질을 바꾸려면 관찰 결과를 보존하고 별도 설계 변경안을 승인받는다.

#### M3의 최소 행동 범위

최초 판단 엔진은 다음 세 행동만 다룬다.

| 행동 | 대상 | M3에서 하는 일 |
|---|---|---|
| A00 현재 행동 유지 | 대상 없음 | 항상 존재하는 기준 후보, 효용 0 |
| A04 도움 요청 | 도움을 요청할 가구 대표 | 자격을 만족하는 대상별 후보 생성과 효용 평가 |
| A11 절도 | 알고 있는 공동창고 | 자격을 만족하는 대상별 후보 생성과 효용 평가 |

행동 ID만으로 후보를 식별하지 않는다. 대상이 다른 행동은 서로 다른 후보다. 자격이 없는 행동은 점수를 낮춰 남기지 않고 후보에서 제외하며 제외 이유를 감사 기록에 남긴다.

A00은 항상 존재한다. A04와 A11은 행위자가 가진 상태·관계·주관적 정보로 자격을 판단한다. 객관적 세계에 식량이나 경비가 존재하더라도 행위자가 알거나 믿지 않는다면 그 비공개 사실을 후보 생성과 효용 계산에 사용할 수 없다.

#### 순수 판단 경계

개념적 호출 경계는 다음과 같다.

```text
evaluate(WorldState, DecisionRequest) -> DecisionResult
```

`DecisionResult`에는 최소한 다음 감사 정보가 필요하다.

- 행위자와 판단 키
- 생성된 후보와 대상
- 제외된 후보와 이유
- 후보별 N, G, V, R, M, K, C, T
- 후보별 총효용
- 제한 난수 사용 여부와 재현 키
- 선택된 후보와 선택 근거

판단은 다음을 변경하지 않는다.

- 세계 날짜와 단계
- 인물·가구·관계·사건·정보·기억
- 자원 저장소와 거래 원장
- 굶주림과 건강
- `next_*_id`
- 세계의 순차 RNG 상태
- canonical state JSON과 SHA-256

M3의 `DecisionResult`는 별도 반환 artifact이며 세계 상태에 삽입하지 않는다. legacy `DecisionRecord`와 M1 audit 형식도 변경하지 않는다. 따라서 M3 판단 기록 자체 때문에 canonical state hash가 변하지 않는다.

#### 효용 계산과 제한 난수 경계

결정 14의 구성요소 범위와 가중치는 유지하되 부동소수점 계산을 사용하지 않는다.

```text
U_SCALED =
  30N + 20G + 20V + 10R + 10M
  - 15K - 15C - 5T

표시 효용 U = U_SCALED / 100
```

N, G, V, R, M은 `-100~100`, K, C, T는 `0~100` 범위를 벗어날 수 없다. 각 구성요소를 만드는 정확한 정수식, clamp 순서, 나눗셈과 반올림 규칙은 결정 22에서 동결한다.

최고 후보와 차순위의 표시 효용 차이가 5 이상, 즉 `U_SCALED` 차이가 500 이상이면 난수를 사용하지 않는다. `U_SCALED` 차이가 500 미만이면 세계 시드·날짜·행위자·판단 키·후보를 이용하는 상태 없는 제한 난수를 반드시 사용한다. 후보 저장 순서, 무관한 NPC의 존재 또는 다른 판단 호출 횟수에 결과가 흔들려서는 안 된다. 정확한 키 직렬화와 배분 방식은 결정 22에서 정한다.

#### 최소 의미 계약

특정 최종 방향은 규정하지 않지만 구성요소가 아무 의미도 갖지 않는 것을 허용하지는 않는다.

- 식량 획득 행동에서 식량 부족이 커지면 N 입력 압력이 커진다.
- 행위자가 알고 믿는 위험이 커지면 K 입력 압력이 커진다.
- 규범을 중시하는 행위자가 규범 위반 행동을 평가하면 그 충돌이 C에 반영된다.

이는 개별 입력과 구성요소 사이의 정의다. 다른 구성요소가 상쇄할 수 있으므로 총효용이나 최종 선택의 방향을 보장하지 않는다. 세부 수치와 경계값은 결정 22 전에는 확정하지 않는다.

#### C01~C05 관찰 프로브

각 프로브는 동결 fixture에서 한 묶음의 입력만 바꾸고 후보·구성요소·총효용·선택을 모두 기록한다.

| ID | 비교 상태 | 관찰 내용 | 금지되는 합격 조건 |
|---|---|---|---|
| C01 | 도움 요청과 절도 기회를 모두 안 상태 | 모든 후보·점수·선택 | 도움 요청이 반드시 절도보다 높음 |
| C02 | 요청 거절, 식량·건강·신뢰·분노·기회 인식 변경 | C01 대비 구성요소와 선택 변화 | 절도 효용 또는 선택이 반드시 상승 |
| C03 | 실제로 도움을 받은 상태 | C01·C02 대비 구성요소와 선택 | 절도 압력이 반드시 하락 |
| C04 | 부양가족만 제거한 상태 | 가족 관련 입력과 전체 판단 차이 | 절도 효용이 반드시 하락 |
| C05 | 실제 경비와 알려진 경비를 분리 | 비공개 실제 위험의 무영향과 알려진 위험의 재계산 | 알려진 위험이 특정 최종 선택을 강제 |

C05에서는 행위자가 알지 못하는 실제 경비만 바꾼 두 판단 결과가 같아야 한다. 이것은 행동 방향을 요구하는 결과 oracle이 아니라 주관적 정보 경계의 기계 시험이다. 행위자가 경비 정보를 알게 된 상태는 동결 규칙으로 다시 계산하되 결과 방향은 관찰만 한다.

#### 승인과 다음 게이트

결정 21은 관찰 우선 계약을 고정했다. 세부 schema·정수 계산·제한 난수·fixture와 구현 파일은 결정 22를 따른다.

### 결정 22. M3 세부 구현 명세

결정 22와 후속 `M3 구현 승인`에 따라 다음을 동결한다.

#### schema와 입력 경계

- `SCHEMA_VERSION_M3 = 3`, `CURRENT_SCHEMA_VERSION = 3`
- ruleset ID는 `drought-prototype-rules-v3`
- schema 1·2 자동 migration은 하지 않으며 기존 동결 artifact를 그대로 보존한다.
- `InformationState`에 `fact_type_id`, `subject_kind`, `subject_id`, `belief_value`를 추가한다.
- 유효 믿음값은 `ROUND_DIV(belief_value × confidence, 100)`이다.
- 같은 소유자·사실 유형·대상 조합은 하나만 허용한다.
- `HouseholdState.dependent_person_ids`는 `member_ids`의 부분집합이다. legacy `dependency_load`는 M3 판단에서 읽지 않는다.
- `ResourceStoreState.security_level`은 객관적 실제값이지만 M3 판단에서는 읽지 않는다.
- 자연어 `claim`, 사건, 기억, 외부 실제 식량·보안, 대상의 사적 상태와 `player_person_id`는 판단 입력이 아니다.

구조화된 사실 유형은 다음으로 제한한다.

| 대상 | 사실 유형 |
|---|---|
| person | `request_food_access`, `request_food_capacity`, `request_success_expectation`, `request_social_risk`, `village_authority` |
| resource_store | `food_stock_level`, `theft_access`, `theft_opportunity`, `detection_risk`, `sanction_severity` |

`request_food_access`와 `village_authority`의 `belief_value`는 0 또는 100만 허용한다. 후보에 필요한 구조화된 사실이 하나라도 없으면 기본값을 발명하지 않고 후보를 제외한다.

#### 순수 평가 API와 artifact

```text
DecisionEngine.evaluate(WorldState, DecisionRequest) -> DecisionResult
```

`DecisionRequest`는 `actor_person_id`, `decision_key`만 가진다. `DecisionResult`는 입력 상태 hash, ruleset hash, 후보별 입력 사실과 N·G·V·R·M·K·C·T, 총효용, 제외 이유, 선택 방식과 제한 난수 감사값을 보존한다. 이 결과는 별도 canonical artifact이며 세계 상태와 세계 hash에 삽입하지 않는다.

M3 평가는 세계 날짜·자원·상태·순차 RNG를 변경하지 않는다. 상대 응답, 절도 성공·발각, 자원 이전과 사건·기억·관계·성향 변화는 M4 이후의 책임이다.

#### 후보 자격

- `A00||`은 항상 정확히 한 번 존재하고 모든 구성요소가 0이다.
- A04는 식량 압력이 양수이고 `goal:secure_household_food`가 있으며, 같은 사람에 대한 요청 사실 네 개가 모두 있고 유효 접근값이 50 이상일 때 생성한다.
- A11은 같은 목표·압력 조건에서 같은 저장소에 대한 절도 사실 다섯 개가 모두 있고 유효 재고가 1 이상, 접근·기회가 각각 50 이상일 때 생성한다.
- 행위자 자신과 자기 가구 저장소는 대상에서 제외한다.

후보 ID는 각각 `A00||`, `A04|person|<person-id>`, `A11|resource_store|<store-id>` 형식이다.

#### 정수 계산

모든 나눗셈은 부동소수점 없이 다음 반올림을 사용한다.

```text
ROUND_DIV(n,d) = sign(n) × floor((2 × abs(n) + d) / (2 × d))
```

이는 정확히 절반인 값을 0에서 먼 방향으로 반올림한다. 총효용은 결정 21의 `U_SCALED`를 그대로 사용한다.

- N은 가구 생존 인원의 10일 필요량 대비 자기 가구 식량 부족, 최대 굶주림과 최대 4명의 명시적 부양가족 배수를 결합한다.
- G는 승인된 식량 확보 목표를 가진 유효 후보에서 100이다.
- V는 `family_protection`, `community_survival`, `legitimate_order`, `fairness_reciprocity`, `property_autonomy`, `life_protection`과 행동별 의미 profile의 정수 내적이다.
- R은 행위자에서 대상으로 향하는 관계와 부양가족 유대만 사용한다. 절도의 권위자 노출 손실은 행위자가 `village_authority`라고 믿는 사람의 관계와 알려진 발각 위험만 사용한다.
- M은 요청의 알려진 수용능력·성공기대 최솟값 또는 절도의 알려진 재고·접근·기회 최솟값이다.
- K는 알려진 기본 위험에 `risk_taking`과 현재 `fear`를 적용한다.
- C는 규범 준수와 정당 질서를 반영하며 A04는 0, A11은 규범 위반 100을 사용한다. 창고 직원·경비 역할에는 의무 위반도 더한다.
- T는 A00=0, A04=25, A11=50이다.

정확한 의미 profile, 계수, clamp 순서와 ruleset hash 입력은 `M3DecisionRules.to_data()`가 실행 가능한 단일 기준이다.

#### 선택과 상태 없는 제한 난수

후보는 총효용 내림차순, 후보 ID 오름차순으로 정렬한다. 양수인 비-A00 후보가 없으면 A00을 고른다. 최고·차순위 차이가 500 이상이면 최고 후보를 난수 없이 선택한다.

차이가 500 미만이면 최고점과의 차이가 500 미만인 후보 중 음수 비-A00을 제외하고 근접 후보군을 만든다. 가중치는 `500 - (최고점 - 후보점)`이다. 알고리즘 ID, 세계 seed, 날짜, 행위자, 판단 키와 ID 순으로 정렬한 후보·점수·가중치를 canonical JSON으로 직렬화해 SHA-256을 구한다. 앞 15 hex의 60-bit 정수를 총가중치로 나눈 나머지를 사용한다. 세계의 순차 RNG 상태는 소비하지 않는다.

#### 동결 관찰 fixture

C01~C05는 3인 가구의 가구주, 배우자·자녀, 촌장과 공동창고를 사용하는 고정 입력이다. C05A와 C05C는 알려진 위험이 같고 실제 보안만 다르므로 입력 세계 hash는 달라도 `input_state_hash`를 제외한 판단 core가 같아야 한다. C05B는 알려진 위험도 다르게 해 재계산만 관찰한다.

최초 기계적으로 올바른 실행 결과를 `tests/fixtures/m3_observation_report.json`과 `.sha256`에 동결했다. 모든 C01~C05 상태에서 A04가 선택됐지만 이것은 합격 조건도 인간다움의 증거도 아니다. 동결 artifact hash는 다음과 같다.

```text
2b4a65a99fcf795999ee4a8e34f9ace9a0b791e659a631b8efa1b34da8602357
```

결정 22 구현은 M3-T01~T12, M3-R01~R04와 추가 schema·입력 경계 회귀 시험을 통과해야 한다. M4 구현은 결정 23 승인만으로 시작하지 않으며, 세부 구현 명세와 별도의 구현 승인을 기다린다.

## 25. 승인된 잠정 설계 23

### 결정 23. M4 원자적 행동 결과 처리 계약

M4는 M3가 고른 행동을 현실 세계의 실제 결과로 해소한다. 원하는 행동이나 이야기 결과를 만들기 위한 계층이 아니며, 동일한 입력과 동결 규칙에서 재현 가능하고 감사 가능한 결과를 만드는 계층이다.

고수준 아키텍처는 승인·동결됐지만 M4 구현은 아직 승인되지 않았다. 필드 타입, 정수 계수와 공식, 정확한 RNG 키 직렬화, `action_instance_id` 생성 규칙, fixture 및 M4-T/R 시험은 결정 24에서 별도로 고정한다.

#### 책임 경계

```text
M3 = 무엇을 할 것인가
IntentParameterizer = 그 선택을 어떤 구체적 시도로 만들 것인가
M4 = 실제 세계에서는 무엇이 일어났는가
M5 = 일어난 일을 사람들이 어떻게 알고 기억하고 받아들이는가
```

M4는 관계·기억·감정·성향을 직접 바꾸지 않는다. 대신 M5가 객관적 사건과 인물별 인식으로 변환할 수 있는 목격·흔적 등 객관적 evidence seed를 출력한다.

#### 최초 지원 범위

| 행동 | 내용 | 결과 유형 |
|---|---|---|
| A00 | 현재 행동 유지 | R0 확정 처리 |
| A04 | 다른 인물에게 식량 요청 | R1 상대방 판단 |
| A11 | 공동창고 절도 시도 | R3 대항 행동 |

A04 응답은 `GRANT_FULL`, `GRANT_PARTIAL`, `REJECT`만 허용한다. 이번 단계에서 `COUNTEROFFER`는 지원하지 않는다. 응답자의 식량 출처는 응답자 가구의 `resource_store_id` 하나로 제한한다.

R2 불확실 과업과 A02 공동창고 실사는 이번 M4 범위 밖이다. 장기 설계의 R2 분류 자체를 폐기하는 것이 아니라, A11만으로 수행·실패·노출 분리를 먼저 검증하기 위해 연기한다.

schema 4에는 A11 수행 계산에 필요한 최소 능력·기술 값을 담을 정적 타입 container를 추가할 수 있다. 이번 단계는 container와 직접 참조 규칙만 정의하며 성장, 경험치, 파생 능력치, 광범위한 직업 보정이나 완성된 캐릭터 능력 체계는 구현하지 않는다. 이는 결정 15의 임시 기존 정보 조합을 M4의 감사 가능한 명시 입력으로 좁혀 교체하는 것이며, 정확한 필드와 허용 key는 결정 24에서 동결한다.

#### 처리 pipeline과 원자성

```text
M3 DecisionResult
→ canonical provenance 재검증
→ IntentParameterizer
→ Fully Parameterized ActionIntent
→ 객관적 실행 가능성 재검증
→ A04 responder decision / A11 performance
→ desired / attempted / proposed result
→ resource conflict resolution
→ actual result와 objective attainment
→ exposure / witness / trace
→ deterministic resource ledger
→ clone-world apply
→ global invariant validation
→ atomic commit
```

복수 행동은 입력 배열 순서가 아니라 안정적인 `action_instance_id` 순으로 처리한다. 제안된 모든 자원 변화와 충돌을 확정한 뒤 거래 원장의 순서를 부여한다. 하나라도 전역 invariant를 깨뜨리면 원본 세계를 변경하지 않고 batch 전체를 실패시킨다.

#### ruleset manifest

schema 4의 세계는 단일 ruleset ID·hash 대신 다음 다섯 component를 가진 manifest를 사용한다.

```text
resource
decision
parameterization
response
resolution
```

각 component의 ID와 canonical hash로 `simulation_ruleset_hash`를 만든다. 어느 component의 규칙이 바뀌어도 전체 simulation ruleset hash가 바뀌어야 한다. M1~M3의 동결 artifact와 legacy schema는 재작성하지 않는다.

#### DecisionResult와 intent provenance

`IntentParameterizer`는 임의의 행동 문자열을 받지 않는다. 기존 API인 다음 호출로 입력 세계에서 M3 결과를 다시 계산한다.

```text
DecisionEngine.evaluate(WorldState, DecisionRequest) -> DecisionResult
```

재계산 결과의 canonical hash가 제출된 `DecisionResult`와 같아야 하며, actor, decision key, input state hash, decision ruleset hash와 selected candidate가 모두 일치해야 한다. 완전한 intent는 최소한 다음 provenance를 보존한다.

```text
source_decision_hash
source_decision_input_state_hash
source_decision_ruleset_hash
source_selected_candidate_id
parameterization_ruleset_hash
```

`action_instance_id`는 전역 순차 allocator나 입력 배열 위치에서 만들지 않는다. 동일한 행위자가 같은 판단 키·행동·대상을 반복할 때도 충돌하지 않도록 `decision_instance_key` 또는 안정적인 `attempt_ordinal`을 입력 계약에 포함해야 한다. 둘 중 어느 방식을 쓸지와 정확한 canonical 생성식은 결정 24에서 고정한다.

#### IntentParameterizer의 정보 경계

Parameterizer는 의도 형성 계층이므로 행위자가 아는 정보만 사용한다.

허용되는 입력은 다음과 같다.

- 행위자 자신의 건강·욕구와 직접 소속된 가구의 자기 권위 상태
- 행위자의 구조화된 주관적 사실
- M3가 선택한 행동과 대상
- 동결된 parameterization rules

금지되는 입력은 다음과 같다.

- 대상 창고의 비공개 실제 재고와 실제 보안
- 숨어 있는 목격자와 행위자가 알지 못하는 현장 상태
- 대상 인물의 비공개 욕구·감정·자원 상태

A11의 `desired_units`는 가구 필요량, 행위자가 믿는 목표 창고 상황과 행동별 상한으로 정한다. 실제 목표 창고 수량은 M4의 현실 해소 단계에서만 사용한다. 따라서 잘못된 정보로 빈 창고를 털려는 시도도 사라지지 않고 실제 실패·목격·흔적으로 이어질 수 있다.

#### 실행 불가와 현실적 실패의 경계

객관적 재검증은 행동을 시작할 수 없는 경우에만 `INVALIDATED`를 반환한다.

```text
INVALIDATED 예시
- actor가 사망함
- 필수 target이 소멸함
- actor가 실행 현장에 없음
- 행동에 필수적인 대상 자체가 더 이상 존재하지 않음
```

다음은 실행 무효가 아니라 가능한 한 `RESOLVED`의 현실 조건으로 처리한다.

```text
- 실제 창고가 비어 있음
- 실제 경비가 예상보다 강함
- 응답자에게 제공할 식량이 없음
```

즉 `잘못된 정보 → 잘못된 선택 → 현실과 충돌`을 보존한다. `ResolutionContext`는 임의의 호출자가 조립하는 공개 입력이 아니라 신뢰된 scheduler 또는 execution issuer만 생성한다. canonical context는 최소한 issuer ID, 입력 state hash, 날짜·phase와 해당 `action_instance_id` 묶음에 결합하며, resolver는 현재 세계·batch와 일치하지 않거나 이미 소비된 context의 재사용을 거부한다. 암호학적 서명이나 네트워크 인증은 이 로컬 프로토타입의 범위가 아니다.

context는 존재하고 살아 있는 현장 인물, 중복 부재, 행위자의 현장 포함도 검증한다. 아직 위치 scheduler가 없으므로 실제 위치를 판정해 context를 발행하는 책임은 외부 execution-context trust boundary이며 M5·M6의 scheduler가 후속 책임을 갖는다. M4 시험에서는 production scheduler를 가장하지 않는 명시적 test issuer만 사용하며, 정확한 발행·소비 API와 replay 식별자는 결정 24에서 고정한다.

#### 결과 축과 절도 수량

행동 결과는 한 개의 성공 boolean으로 축약하지 않는다.

```text
processing_status = RESOLVED / INVALIDATED / REJECTED_AS_MALFORMED
objective_attainment = FULL / PARTIAL / NONE / NOT_APPLICABLE
response_decision = GRANT_FULL / GRANT_PARTIAL / REJECT / NOT_APPLICABLE
```

A11은 최소한 다음 수량을 구분한다.

```text
desired_units   = 행위자가 바라며 intent에 고정한 양
attempted_units = 현실에서 실제로 훔치려 한 양
proposed_units  = 자원 충돌 전 획득 가능 결과
actual_units    = 충돌 해결과 원장 적용 후 실제 획득량
```

필요하면 `performance_capacity_units`를 감사용 중간값으로 추가한다. 노출·목격·흔적 계산은 `actual_units`만 보지 않고 시도량, 실제량, 수행 결과, 가시성, 은밀성, 목격자 지각과 실제 보안을 행동별 resolution rules로 사용한다. 그러므로 실제 획득량이 0이어도 목격되거나 흔적을 남길 수 있다.

#### 결정론적 난수와 거래 identity

M4 결과 난수는 세계 전체 hash나 순차 RNG 호출 횟수에 묶지 않는다. 정확한 키는 결정 24에서 정하되 최소한 simulation ruleset, seed, 날짜·phase, 안정적인 action instance, roll purpose와 필요한 participant를 canonical 직렬화한 상태 없는 행동 단위 키를 사용한다.

M4가 새로 만드는 거래 ID는 `action_instance_id + transfer_leg`에서 파생되는 action-scoped deterministic ID를 사용한다. 자원 충돌을 해결하고 행동을 canonical 정렬한 뒤 `sequence_index`를 부여한다. batch 내 전역 sequence나 무관한 앞선 행동 때문에 개별 행동의 의미론적 resolution hash가 바뀌어서는 안 된다. M2의 기존 동결 거래 ID와 artifact는 변경하지 않는다.

#### 출력 계약

M4는 최소한 다음을 반환한다.

```text
BatchResolutionRecord
committed_outcomes: ActionOutcomeRecord[]
committed_witness_seeds: WitnessObservationSeed[]
committed_transactions: ResourceTransactionRecord[]
next_world: WorldState or absent
```

`BatchResolutionRecord`는 개별 행동의 `processing_status`와 별도로 다음 batch 수준 정보를 가진다.

```text
batch_status = COMMITTED / REJECTED
input_state_hash
output_state_hash or absent
errors[]
```

`next_world`와 세 `committed_*` 배열은 전역 invariant 검증과 atomic commit이 성공한 경우에만 반환한다. batch가 `REJECTED`이면 `next_world`는 없고 세 배열은 비어 있어야 하며, 적용되지 않은 proposed outcome이나 거래를 committed 결과로 노출해서는 안 된다. 실패 원인 분석이 필요하면 별도의 비세계·비commit `attempt_diagnostics`에 기록하고 committed artifact 및 세계 hash와 구분한다.

각 committed 결과는 intent provenance, 처리 상태, 목적 달성, 상대 응답, 희망·시도·제안·실제 수량, 수행과 노출의 감사값, 자원 거래 ID 및 객관적 evidence seed를 재구성할 수 있어야 한다.

#### 승인과 다음 게이트

결정 23은 M4의 고수준 아키텍처만 동결한다. 다음 작업은 결정 24 `M4 세부 구현 명세`이며 다음을 반드시 확정해야 한다.

- schema 4의 정확한 필드와 정적 타입
- parameterization·response·resolution의 모든 정수식과 clamp·반올림 순서
- exact RNG key serialization과 roll purpose 목록
- 중복 없는 `action_instance_id`의 유일성 출처와 생성식
- stable transaction ID와 ledger sequence 규칙
- 기준 fixture, 관찰 report 및 M4-T/R 시험 목록
- `INVALIDATED`와 현실적 `RESOLVED/NONE`의 행동별 경계
- 신뢰된 `ResolutionContext` issuer, state/action binding과 replay 거부 규칙
- batch commit 상태, 실패 출력 및 `next_world` 부재 계약

별도의 `M4 구현 승인` 전에는 schema 4 코드, resolver, fixture 또는 시험을 구현하지 않는다.

## 26. 승인된 잠정 설계 24

### 결정 24. M4 세부 구현 명세

결정 24는 기준 `main@434cf7f92dffc5bf9cd94bc17f9a5e228600e445`에서 독립 레드팀 검산을 통과했고 2026-09-04 사용자가 최종 승인했다. 이 결정은 앞서 작성된 모든 Decision 24 후보·수정안·요약본을 대체한다.

```text
DECISION 23 = APPROVED
DECISION 24 = APPROVED
M4 DETAILED DESIGN = FROZEN
M4 IMPLEMENTATION = NOT AUTHORIZED
SCHEMA 3→4 AUTOMATIC MIGRATION = OUT OF SCOPE
SCHEMA 1–3 FROZEN SUPPORT = PRESERVED
```

#### 1. M4 범위와 책임 경계

M4는 M3가 선택한 행동을 객관적 세계에서 원자적으로 처리한다.

```text
M3 = 행위자가 자기 정보로 무엇을 할지 선택
Parameterizer = 선택을 수량과 대상으로 구체화
M4 = 실제 세계에서 무엇이 발생했는지 확정
M5 = 발생 사실을 누가 알고 기억하며 어떻게 변하는지 처리
```

최초 지원 행동은 다음 세 개뿐이다.

| Action | 의미 | M4 처리 |
|---|---|---|
| `A00` | 기다림/행동 유지 | 수행 기록, 자원 변화 없음 |
| `A04` | 식량 요청 | 상대의 독립 응답과 실제 이전량 확정 |
| `A11` | 절도 | 수행량, 실제 획득량, 흔적과 목격 확정 |

`A02`, 협상 counteroffer, 기억·소문·관계 변화, 하루 전체 scheduler, 위치 이동 및 권한 시스템은 범위 밖이다.

#### 2. 공통 수치·정규화 계약

모든 수치는 별도 명시가 없으면 signed 64-bit 계산 중간값을 사용하고, 저장되는 게임 점수와 수량은 `0..2147483647` 범위의 정수다. overflow 가능성은 mutation 전에 거부한다.

```text
round_div(n, d), d > 0

n == 0 → 0
n > 0  → floor((2*n + d) / (2*d))
n < 0  → -floor((2*abs(n) + d) / (2*d))
```

정확히 half-away-from-zero다.

```text
ceil_div_nonnegative(n, d)
= floor((n + d - 1) / d)

precondition: n >= 0, d > 0
```

모든 곱셈, 나눗셈, clamp는 이 문서에 쓰인 순서대로 적용한다. 부동소수점 계산을 금지한다.

`StateCanonicalizer`의 현재 계약을 그대로 사용한다.

- dictionary key: 사전식
- 문자열 배열: 사전식
- 모든 원소가 `id`를 가진 dictionary 배열: `id` 사전식
- 그 외 배열: 생산자가 명시적으로 정렬한 순서 보존

#### 7. IntentParameterizer

##### 7.1 API와 정보 경계

```text
parameterize(
  world,
  decision_request,
  submitted_decision_result

```

Parameterization 실패는 다음 rank의 첫 오류 하나만 반환하고 `intent=null`로 둔다.

```text

1 decision_provenance_mismatch
2 selected_positive_action_has_zero_need_basis
3 request_source_equals_recipient
4 theft_target_equals_recipient
```

`unsupported_decision_key`는 request의 key가 `daily_food_strategy`가 아닐 때 발생한다. §6.2의 provenance 조건 중 하나라도 실패하면 세부 내부 원인을 외부 artifact에 분산하지 않고 `decision_provenance_mismatch` 하나로 정규화한다. 이 두 오류는 intent가 만들어지기 전 발생하므로 `action_instance_id=""`를 사용한다.

Parameterizer는 의도 형성 계층이다.

허용 입력:

- 행위자 자신과 자기 가구의 self-authoritative 상태
- 행위자가 소유한 주관적 InformationState
- 검증된 M3 selected candidate
- parameterization rules

금지 입력:

- 대상 창고의 actual quantity
- 대상의 actual security
- 대상의 hidden state

##### 7.2 필요량

```text
household_need_10d =
sum(alive household member.daily_food_need_units) * 10

own_food =
actor household resource store의 actual food quantity

food_shortfall =
max(0, household_need_10d - own_food)

max_household_hunger =
max(alive household member.need_scores.hunger)

hunger_relief_floor =
1 if max_household_hunger > 0 else 0

need_basis_units =
max(food_shortfall, hunger_relief_floor)
```

살아 있는 가구원이 한 명도 없으면 합계와 최댓값은 다음으로 고정한다.

```text

max_household_hunger = 0
food_shortfall = 0
hunger_relief_floor = 0
need_basis_units = 0
```

##### 7.3 A04


Parameterizer는 selected target person의 현재 household에서 request source store를 구조적으로 도출한다. 그 store가 recipient store와 같으면 `request_source_equals_recipient`로 실패한다. 수량·security 같은 대상의 숨은 상태는 읽지 않는다.

##### 7.4 A11

선택 target의 `food_stock_level` 주관 fact를 사용한다.

```text
effective_food_stock_level =
round_div(belief_value * confidence, 100)

max(1, ceil_div_nonnegative(effective_food_stock_level * 10, 100))
```

외부에 공개되는 유일한 실행 진입점은 다음 facade다.

```text

  world,
  decision_submissions,
  trusted_context_issuer

- decision_request

```

Facade는 각 submission을 `IntentParameterizer`로 검증·구체화한다. 하나라도 실패하면 첫 parameterization 오류를 batch `REJECTED`로 변환하고 context 발행 및 Resolver 호출을 하지 않는다. 모두 성공하면 trusted issuer가 생성된 action ID별 context를 발행하고 facade가 내부 `ResolutionBatchRequest`를 구성한다.

내부 호출은 다음으로 고정한다.

```text
AtomicActionResolver.resolve_trusted_v1(
  world,
  batch_request,
  trusted_context_issuer
) -> BatchResolutionRecord
```

최초 구현은 프로세스 내부 trust boundary다. 암호학적 서명과 일반 권한 시스템은 도입하지 않는다. 시험은 `TestResolutionContextIssuer`를 사용한다.

`ActionIntent`, `ResolutionContext`, `ResolutionBatchRequest`는 모두 같은 프로세스 내부 신뢰 경계에 속한다. 외부 save, UI, network 또는 임의 JSON에서 decode한 이 객체들을 Resolver에 직접 제출하는 API는 제공하지 않는다. M4 facade만 `IntentParameterizer`와 trusted issuer의 성공 결과를 Resolver로 전달한다.

Resolver는 intent의 exact keyset, `intent_hash`, action/context binding과 stale 상태는 검증하지만, 공격자가 전체 intent와 hash를 함께 다시 만든 **자기 일관적인 위조 provenance**를 탐지한다고 주장하지 않는다. T04는 Parameterizer의 DecisionResult 재검증과 신뢰 경계 이후의 accidental mutation 탐지만 보장한다.

`ResolutionBatchRequest.to_data()` exact keyset:

```text
intents
execution_contexts
```

두 배열은 caller 순서와 무관하게 resolver가 `action_instance_id`순으로 정렬한다. 다음 집합은 정확히 같아야 한다.

```text
set(intents.action_instance_id)
== set(contexts.action_instance_id)
```

#### 10. Batch rejection, INVALIDATED, RESOLVED

##### 10.1 Batch `REJECTED`

다음 구조·위조·stale 오류는 world를 변경하지 않는다. Facade와 Resolver는 함께 §16.7의 reason precedence를 공유하며 **처음 성립하는 오류 하나에서 종료**한다. Parameterization 단계에서 먼저 거부되면 Resolver는 호출되지 않는다. 다중 오류 수집은 최초 M4 범위 밖이다.

복수 submission에서 실패 후보가 동시에 나오면 먼저 전역 `reason precedence`를 비교하고, 같은 rank에서는 diagnostic에 기록할 `action_instance_id`를 소문자 문자열 사전식 오름차순으로 비교한다. action ID를 만들 수 없는 오류는 빈 문자열을 사용하므로 가장 먼저 온다. 두 비교값이 모두 같으면 동일한 rejection 출력 하나로 축약한다. caller의 submission 배열 순서는 선택에 영향을 주지 않는다.

- 잘못된 schema/world/envelope
- manifest 또는 component hash 불일치
- stale input state hash/epoch/day/phase
- facade의 unsupported decision key 또는 잘못된 DecisionResult provenance
- 이미 소비한 decision slot
- 중복 slot/action/context
- intent hash/action ID 불일치
- context hash/issuer 불일치
- intent/context action ID 집합 불일치
- present 배열의 중복·비정규 순서·존재하지 않는 ID
- 지원하지 않는 action
- 필드 타입·범위·exact keyset 위반
- resource sequence 또는 정수 계산 overflow
- clone 적용 후 invariant/conservation/hash 실패

`REJECTED` 결과:

```text
next_world = null
output_state_hash = ""
output_resolution_epoch = -1
committed_outcomes = []
resource_transactions = []
witness_evidence_seeds = []
attempt_diagnostics = rejection diagnostics
```

정확한 rejection 출력:

```text
errors = [first_reason_id]
attempt_diagnostics = [exactly one AttemptDiagnostic]

world를 정상적으로 hash/decode할 수 없음:
input_state_hash = ""
input_resolution_epoch = -1

world를 읽을 수 있음:
input_state_hash = StateHasher.hash_world(world)
input_resolution_epoch = world.resolution_epoch
```

Action에 귀속할 수 없는 오류의 diagnostic `action_instance_id=""`다. 귀속 가능한 오류는 제출물에서 정상적으로 읽힌 action ID를 사용한다. Batch hash는 이 sentinel을 포함한 rejection record에서 정상적으로 생성한다.

##### 10.2 개별 `INVALIDATED`

구조적으로 정상적인 제출이지만 행동 자체를 시작할 수 없는 현실 조건이다.

```text
actor_not_alive
actor_not_present
target_person_missing
target_person_not_alive
target_person_not_present
target_store_missing
target_store_not_present
```

해당 action만 무효화하며 다른 action은 계속 처리한다. `INVALIDATED`도 성공한 batch의 slot을 소비하고 epoch를 증가시킨다.

여러 무효 조건이 동시에 성립하면 적용 가능한 reason을 모두 모아 중복을 제거하고 사전식 정렬한다. 결과는 다음으로 고정한다.

```text
processing_status = INVALIDATED
objective_outcome = NOT_APPLICABLE
details = {}
random_draws = []
resource_transaction_ids = []
witness_evidence_seed_ids = []
```

##### 10.3 `RESOLVED/NONE`

다음은 행동을 실제로 시도했으므로 invalidation이 아니다.

- 대상 창고 재고 0
- responder surplus 0
- 높은 실제 security
- 낮은 performance
- 동시 충돌로 actual 0
- 요청 거절

#### 11. A04 응답 공식

Source store는 responder의 현재 household `resource_store_id`로 제한한다.

```text
reserve_need =
sum(alive responder household member.daily_food_need_units) * 10

surplus =
max(0, source_store.food_quantity - reserve_need)
```

항상 `REJECT` 후보가 있다.

```text
REJECT:
authorized_units = 0
utility = 0
```

Grant 후보:

```text
surplus >= requested_units
→ GRANT_FULL, authorized_units = requested_units

0 < surplus < requested_units
→ GRANT_PARTIAL, authorized_units = surplus

surplus == 0
→ grant 후보 없음
```

누락된 trait/value/relation 성분은 0으로 계산하고 exact 경로를 `defaulted_inputs`에 기록한다.

Exact path 문법:

```text
persons[<person_id>].<domain>.<key>
relations[<source_person_id>-><target_person_id>].<component>
```

예:

```text
persons[person:000004].trait_scores.empathy
relations[person:000004->person:000001].trust
```

관계 record 자체가 없으면 `trust`, `affection`, `obligation`, `fear`, `resentment` 다섯 경로를 각각 기록한다. 배열은 중복 없이 사전식 정렬한다.

```text
care_score =
round_div(
  empathy
  + community_survival
  + fairness_reciprocity
  + life_protection,
  4
)

relation_score =
clamp(
  round_div(
    trust + affection + obligation - fear - resentment,
    3
  ),
  -100,
  100
)

reserve_cost =
round_div(authorized_units * 100, surplus)

grant_utility =
20 * care_score
+ 10 * relation_score
- 20 * reserve_cost
```

동률 후보 순서는 `[grant, REJECT]`다. `A04_RESPONSE_TIE` draw의 `mapped_value`를 index로 사용한다.

후속 자원 충돌로 actual이 줄어도 `response_decision`과 `response_authorized_units`는 변경하지 않는다.

#### 14. 동시 자원 충돌

모든 action의 `proposed_units`를 먼저 계산한다. 같은 source store의 A04와 A11을 하나의 outgoing pool에서 처리하며, 같은 batch의 inbound 자원은 재사용하지 않는다.

용량 `capacity`와 양수 claim `p[i]`:

```text
sum(p) <= capacity
→ actual[i] = p[i]

sum(p) > capacity
→ base[i] = floor(capacity * p[i] / sum(p))
→ remainder = capacity - sum(base)
→ action_instance_id 오름차순으로
  proposed에 아직 도달하지 않은 claim에 1씩 배정
```

그 결과 A04 actual 합이 responder surplus를 넘으면:

1. A04 claim만 surplus 한도로 다시 비례 배분한다.
2. `remaining_for_theft = actual_stock - final_grant_total`을 계산한다.
3. A11 claim을 remaining capacity에서 다시 비례 배분한다.

보장:

```text
0 <= actual_units <= proposed_units
source별 total actual <= input actual stock
source별 A04 actual 합 <= responder surplus
```

Objective:

```text
A04 FULL    ↔ actual == requested
A04 PARTIAL ↔ 0 < actual < requested
A04 NONE    ↔ actual == 0

A11 FULL    ↔ actual == desired
A11 PARTIAL ↔ 0 < actual < desired
A11 NONE    ↔ actual == 0
```

#### 18. Schema 4 DayProcessor

Schema 2 분기는 현재 동작과 fixture/hash를 그대로 보존한다.

Schema 4 분기 순서:

1. 입력 WorldState와 exact keyset을 검증한다.
2. manifest와 `simulation_ruleset_hash`를 재계산한다.
3. `manifest.resource`, `manifest.resolution`을 현재 구현과 대조한다.
4. `day_phase == DAY_END`를 검증한다.
5. metadata `schema_version/ruleset_manifest/simulation_ruleset_hash`와 state를 깊은 복제한다.
6. 소비 계획을 `(household_id, person_id)`순으로 만든다.
7. 시작 sequence를 `next_resource_sequence_index`로 사용한다.
8. 필요한 transaction 수와 counter overflow를 mutation 전에 검사한다.
9. 소비 ID는 기존 `IdAllocator.next_id(world,"resource_transaction")`를 clone에서 사용한다.
10. ResourceService 적용, hunger, health, reconciliation, conservation을 수행한다.
11. `day_index += 1`과 counter 갱신을 완료한다.
12. `resolved_decision_slot_ids=[]`로 초기화한다.
13. 이 최종 상태를 validation하고 state hash를 계산한다.
14. 모든 검증과 hash가 성공한 경우에만 commit한다.

`resolution_epoch`은 보존한다. 실패하면 원본 world, counter, slot 및 `next_ids`를 변경하지 않는다.

#### 24. 관찰 시나리오

F01–F10은 특정 결과가 인간적으로 옳거나 재미있다는 PASS oracle이 아니다. 다음을 관찰·보존한다.

- 요청에서 care/relation/reserve 변화가 응답 계산에 미치는 영향
- 같은 주관 정보에서 실제 security만 달라질 때 실행 결과 변화
- 빈 창고를 잘못 믿고 시도한 행동의 객관적 실패와 노출
- 동시 claim의 순서 독립성
- hunger floor 동작
- 연속 M4 batch와 다음 날 소비 연결

상수나 fixture 변경이 필요하면 기존 값을 조용히 고치지 않는다. ruleset version과 Decision 기록을 갱신한다.

#### 25. 독립 검증 및 승인 기록

독립 레드팀은 문서의 exact ruleset JSON, annex 원상, 정상 fixture 13개와 경계 fixture 6개를 재계산했다. E04 관계 참조 무결성, facade의 동순위 실패 선택, E05 vector hash domain, E06 submission permutation 독립성과 `AtomicActionResolver` 명칭을 포함해 blocker가 모두 닫혔고 신규 blocker는 발견되지 않았다.

비차단 권고인 서로 다른 reason rank 사이의 submission permutation 검증은 `M4-T22`로 추가했다. 이는 승인된 ruleset과 hash를 변경하지 않는다.

결정 24의 승인은 설계만 동결한다. 별도의 `M4 구현 승인` 전에는 schema 4 코드, resolver, repository fixture 또는 시험을 구현하지 않는다.
